# 币塔街机 · 网页推币机

浏览器里的 3D 推币机。Three.js 负责渲染，Rapier3D 负责刚体物理，TypeScript + Vite 构建。

没有服务器、没有分数、没有后端存档 —— 打开就是一个满盘的台子（预置 **318 枚币**），
硬币的每一次越线都由真实刚体模拟算出来，不是脚本动画。

---

## 玩法

无尽模式「**xixi 大王大赏**」是唯一的玩法（v3 起战役六关已摘除）。
「撑多久、堆多高」就是全部目标。

- **投币**：左右自动选位，轻点机台投币。币落在推板顶面，被推板的**摩擦拖曳**推向前缘，
  掉进币床（S13 起「台面输送」已归零，见 `constants.ts` 的 `TABLE.conveyor`）
- **越线返筹码**：币心越过得分线即结算。筹码既是局内的投币资源，也是局外图鉴的购买力
- **八种币**（数值的唯一真源是 `src/game/kinds.ts`，下表只是导览）

  | 币种 | 币面 | 返值 | 说明 |
  | --- | --- | --- | --- |
  | 普通铜币 | （无字） | 5 × 概率闸门 | 盘面主体，越线时只有 9% 真的返值（S23 基值 ×5） |
  | 花纹筹码 | 桃 | 1（吃倍率） | 自己带一道 50% 闸门，越过线也要掷一次 |
  | 绿色返币筹码 | ＋ | 2（固定） | 不吃任何倍率，收尾期的复活通道 |
  | 金色大赏币 | 赏 | 5（固定） | 每 30 投注入一枚，方差的主杠杆 |
  | 钻石筹码 | 钻 | 25（固定） | 独立 3D 几何；老虎机四同的排场之一 |
  | 宝箱硬币 | 箱 | 50（固定） | 独立 3D 几何；S16 起从「派演出」改成固定返值 |
  | 催债币 | 债 | **0，反而扣钱** | 越线按余额比例扣一笔（与胡萝卜四连同一张 10%→40% 的表），是「效果型币种」这个形态的第一个真用户 |
  | 票币 | 票 | **0，改发 1 张票券** | 同一条 `effect` 分派的**另一侧**：催债币证明"效果可以出账"，这一条证明"效果可以给另一种货币"。筹码账为 0，票券账 +1 |

- **深度会开始吐效果币**（名单、起注投数、节奏、落点带都在 `src/game/effects.ts` 的 `inject` 表里，
  `Game.dropCoin` 只遍历它 —— 与"币种清单只在 `kinds.ts`"是同一条 P6 纪律）：
  催债币从第 45 投起、每 24 投一枚。设计意图是把「负 EV」从硬约束
  降成软约束之后，仍然有一条**随深度变狠**的抽水在拉长期斜率 —— 递增目标与构筑负责正反馈。
  它对物理没有任何特权：同尺寸、同碰撞体；它也不往盘面加币（是**汇**不是源），所以水量表里 `water = 0` 是真话。
  ⚠️ 但**"扫板 / 抓斗能把它排掉"这句目前兑付不了** ——
  把五个数摆在一起就看出注入带与两条机关的触达带**都不交**：注入带 `effects.ts` 的 `debtCoin.inject.aheadOfLine = [0.2, 0.45]`
  ⇒ z ∈ [0.70, 0.95]，扫板要 `z ≥ 1.00`（`scoreLineZ 1.15 − SWEEP_ZONE 0.15`），抓斗要 `z ≤ 0.44`
  （`|z − pusherFrontZAtRest(−0.16)| ≤ 0.6`），而抓斗的落点 `GRAPPLE_TARGET_Z = 0.95` 就落在注入带的上沿。
  ⇒ 现档这枚币只由推板决定生死：等它被推到 z ≥ 1.00 时扫板才够得到，而那时扫板是**把它推过去**（触发扣款），不是排掉。
  要拍的两条出口记在 `../PLAN.md` 未收尾 ⑥（甲：把注入带挪进扫板带，让"扫不扫"变成真两难，代价是 1d 那批 n≥20 要重跑；
  乙：放宽抓斗的 z 触达，代价是动已标定的机关几何）。
  ⚠️ 注入位置是**得分线前 0.20~0.45 米**，不是随机纵深：早先随机铺放时实测到
  「7 次注入 / 7 次拿到池位 / 0 次结算」——一枚走不到线的催债币作为机制等于不存在。
  ~~上界保证它通常在本局内真的兑现；~~下界原本是想留**反应窗口**，但按上面那五个数，这个窗口现在是空的。
  ⚠️ "通常会在本局兑现"这句被数据削低了：n=20 领卡臂 **注入 61 枚 ⇒ 越线触发 15 次（约 1/4）、被回落洞无损排掉 5 枚，其余 41 枚到局终仍没归宿**
  ⇒ 现档多数催债币是"注入后静静留在盘上"，机制的可见性远低于当初按 n=3 的判断；排掉那 5 枚是**币自己掉进回落洞**，不是玩家用机关排的。
- **票币**（2c 的第二档，`ticketCoin`）：从第 20 投起、每 40 投一枚，注在**得分线前 0.05~0.20 米**。
  它越线**返 0 筹码、发 1 张票券**，所以两种货币各有各的账：筹码恒等式一个字不改（`water = 0` 是真话），
  票券由它自己的恒等式 `tickets === earned − spent` 与分源计数 `ticketBySource.effect` 守
  —— 这条门（`S2 票币真打法接线`）核的就是「流水里 `act === 'ticket'` 记的张数 === 分源那一格」，
  两个口袋不等就是"发了券但没人知道它是谁发的"。
  ★ 落点带比催债币**靠前**是有意的，不是抄来的：**罚的币要留反应窗口，奖的币不用。**
  催债币那 0.20 米是给"玩家还能用机关把它排掉"预留的（目前这条窗口是空的，见上一条与 `../PLAN.md` ⑥）；
  票币越早兑现越好 —— 按催债币那条带的实测兑现率（n=20：注入 61 枚只有 15 枚走到线，约 1/4），
  把发券机制埋在同一个深度上，四分之三的发券机会到局终都不会发生，
  那正是本项目对"机制只存在于代码里"的定义。
  ⚠️ 票券是**第四个发券源**，会让波次目标更容易达到。第一批 n=20 已经判过现档爬坡"太易达到"，
  所以这一档的量级刻意压在点缀级（按同兑现率估 ≈ 每局 1~2 张，对主源约 +5~10 %）；
  **定档（`waves.ts` 的 `WAVE_TARGET_*`）还没做，那一轮要把它算进去。**
  量级已按 n=20 领卡臂实测（票币之后的那批，`/tmp/all-n20.log`，`harness-sha=e69f589381d7e4c5`）：
  **20 局里 18 局遇到票币、共 37 次触发、发券 37 张**，占同批票券总量 380 张的 **9.7 %**（≈1.85 张/局）
  ⇒ 与"点缀级"的设计意图相符，但**它确实让本来就"太易达到"的波次爬坡更松**（见下条与 `waves.ts` 的定档欠项）。
  落点带往前挪也兑现了：同一批里催债币那条带的兑现率只有 **13/62 ≈ 21 %**，
  而票币那条带（0.05~0.20 米）是 **37 次触发 / 注入后基本都走到线** ⇒ "埋在后排的机制等于不存在"这条判断成立。

- **XIXI 集章**：落点按 x 分成 X·I·X·I 四段，币落到币床那一刻点亮对应槽位；
  集齐四槽摇一次背板老虎机。权重表在 `xixi.ts`（`SLOT_OUTCOME_WEIGHTS`，四段同一个 `roll` 轴、**不吃第三条随机数**）：
  `win3 43.5 / win4 1.5 / fine 15 / miss 40` ——
  **三同是常规奖**（投放演出 / 加力），画面上画成「三格同 + 一格环带相邻的差一格」；
  **四同才是大奖**，按图案分四种排场（加力 = 连续 4 发加长行程、
  币塔 = jackpot 级柱数、钻石 / 宝箱 = 对应色的一排喷泉），多吃的 1.8 秒停顿是给仪式的而不是额外随机数；
  **杂牌（miss）无罚**，四格两两不同，「没凑齐」在画面上自证
- **老虎机罚钱罚的是胡萝卜四连，扣的是「余额的一成到四成」**（1a 起改成比例制，标题里的区间就是表的两端）：
  罚金 = 本局余额 × `10% → 40%`，比例随本局投币数线性爬升（`drops / 90` 归一化，表在 `xixi.ts`）
  ⇒ 换掉的是旧版那个「固定 6 枚」：S4 合并账户之后 6 枚只剩身家的 3%，"疼一下"变成了"没感觉"。
  上限 40% 意味着**一次罚款永远扣得掉**（碰不到 0 余额的 clamp），
  所以"扣不掉转欠款"那套 S5b 机器现在是**安全网而不是常规路径**；
  一次罚款也不会把你直接打死，只是把沉降提前——归零仍由既有的破产分支判定。
  不吃任何倍率（加注 / 热度 / 热区都不参与）
- **票券与波次（局内构筑）**：越线每 12 枚发 1 张票券（「票孔」奖励能压到 4），连落到 5 档补发 1 张（每串一次），
  老虎机四同给 2 张。攒够**本波目标**（第 n 波要 `n` 张）就弹出**三选一**：加力包 / 机关充能 / 票孔，
  选一张花 1 张票券。**票券只在本局有效、不进余额恒等式、也不跨局携带** ——
  筹码会被罚金扣光，成长不能挂在它上面；而跪来的脏钱本来也刷不出票券。
- **票券的持久化口径（两件不同的事，别混成一句）**：下一局开局时手里**归零**；而"本局挣了几张"要作为
  **成绩记录的一列**随那一局写进存档 —— 那是历史，不是余额。记的是**挣**那一头，字段名因此叫
  `RunRecord.ticketEarned` 而不是裸的 `tickets`：一张券会被三选一花掉，"挣 12 花 9"与"还剩 3"是两个数，
  持久化记录里只留一个名字必然被读错。
  守它的门是 `1b 落盘对质`：把**引擎内存里那条**（`endless.lastRunRecord`）与 **`localStorage` 解析回来的那条**
  在同一次 `evaluate` 里对质 —— 只看 JSON 抓不到"根本没写这个字段"（两边都缺就恒绿），只看内存抓不到
  "写了但落盘/载入那一趟被吞"（`slice(0, 10)` 与 `parse()` 都是能吞的地方）。
  ⚠️ 老存档里的记录**没有这个键**（`parse()` 对 `runs` 只验一层 `Array.isArray`，不逐条归一化），
  所以它是**可选键**：缺 = "这条记录早于 1b"，不是 0。改成必填要在载入处补 0，那会连带改掉
  `tests/save-migration.spec.ts:336` 那条精确形状断言 —— 验证面改动，要用户点头才走。
  三档奖励**都不往筹码账里加东西**（换的是加力发数 / 机关次数 / 发券间隔），
  所以 `water = 0` 是真话。⚠️ 守它的门（`S2 池水门`，在 `xixi` 模式）断言的是**两张表 `Σwater === 0`**，
  不是"每投总水量不超预算"——后者目前**没有门**：现档每投免费币实测 **[0.43, 1.12] × `FAUCET_BUDGET_PER_DROP`**
  （上段本就压过红线，且成因是老虎机自身而不是新效果，算式唯一真源在 `xixi.ts`）。
  ⇒ 要加"注入币"或"越线返值乘数"这类档，得先把 ② `P(加力已满)` 结清、给 `per-drop` 立一条真门，
  再**有意地**抬这条 `Σwater === 0`——别把它读成"总量守住了"（详见 `../PLAN.md` 收工表 2b 那行）。
  这条读数现在是 `economy` 批的一行 `[info] 2b 池水读数（不进判据）`：分子 = 逐局 `showEvents`
  （`phase === 'completed'`）的 `spawned` 之和（**只数币池真币**——视觉币走 `CoinSpray` 独立通道，天然不在里面，
  于是"哪些演出算水"不需要人肉判定），分母 = 本批投币数，红线从引擎现读（脚本不抄第二份数字）。
  ⚠️ **分子或分母为 0 一律打成「缺席」而不是绿**：实测小批打出 `投币 98 枚｜演出交付免费币 0 枚｜本批摇奖 0 次`，
  而第一版把那个 0 写成「在红线内，= 0.00 × 红线」⇒ 那是把"没测到"写成"测到且合格"，本项目最贵的一类假绿。
  （economy 里摇奖本来就稀，缺席是这一臂的正常形态，不是故障。）
  ★ **2b 那条"总量门"最终立成了确定性棘轮**（`xixi` 模式的 `S2 名义水量棘轮`）：计划原文要的是"每投 ≤ 1.0 ×
  `FAUCET_BUDGET_PER_DROP`"，两条实测把它否了 —— ① 现档每投本就落在 [0.43, 1.12] × 红线（照原文装 = 永久红，
  而永久红的门等于没有门），② 每摇交付是 **1~40 枚**的重尾量而 economy 摇奖极稀（n=20 批只摇 9 次）⇒
  任何贴着均值的抽样界都会随机翻红。落地换成**从活表重算 `xixi.ts` 那段唯一算式**：outcome 权重、符号权重、
  四同池、每场枚数、兜底枚数全部现读，脚本只保留算术和一行上限 ⇒ 零样本、逐位可复现。
  浏览器实测（`xixi` FAST 腿，**39 项 39 过**）：名义 **2.9104** + 兜底上界 **0.4847** = **3.3951 枚/摇奖**（上限 3.40）
  ｜三同均 6.329、四同均 10.500｜每场枚数现读 `tower 16/大奖40、chest 1、diamond 1、fountain 10、gate 7`。
  变异臂在隔离树把 `tower.count` 16→17 ⇒ **39 项 38 过 1 红，红的正是这条棘轮**（3.0347 + 0.4847 = **3.5194**），
  其余 38 条一动不动 ⇒ 扰动隔离成立；跑完已 `sed` 还原并与主树 `diff` 归零。
  ⚠️ 这条门守的是"**谁都不能悄悄往盘面加水**"，**不**守"每投总量 ≤ 红线"——后者仍然没有门
  （现档每投本就落在 [0.43, 1.12] × 红线），由上面那行 `[info] 2b 池水读数` 的打印与这段偏离记录一起承担。
  最新一次真实打法抽样（n=20 领卡臂）：`投币 1630 枚｜演出交付免费币 10 枚｜摇奖 4 次` ⇒ **0.0061 枚/投 = 0.15 × 红线**，
  而同一张机器在另一批 n=20 摇了 9 次 ⇒ 分母跨 **2.3 倍**；所以 0.15× 这个位置**不能**读成"预算还有余量"，
  它跟着摇奖频率一起漂 —— 这正是"不立抽样界、改立活表棘轮"的实测理由。
- **三个机关**（全在局内花筹码）：扫板、抓斗、后装填
  （P7 起「风险转轮」已删除——它的定位由 XIXI 老虎机承接；「加注」是投币档位 1/2/5 筹码 → ×1/×2/×4，不是机关）
- **热度与热区**：连落越多返值越高（3 连 ×1.5 / 5 连 ×2 / 8 连 ×3）；
  得分线上有一条周期性左右扫的亮条，在它范围内越线**再翻一倍**
- **破产是内容，不是惩罚**：输光之后弹的不是「破产窗」而是一条**续玩报价**——
  可以就地借一笔贷款接着玩这一局（欠款进存档，之后每一笔入账按比例先还债），
  也可以「跪求 xixi 大王大赏」拿一笔递减救济（30→24→19→15→12→10）。
  跪来的钱是**脏钱**：它进余额、能接着投，但计入 `beggedTotal`，
  于是 **可花 = 余额 − 累计跪求额**（`SaveStore.spendable`）——
  这是一次性永久折减而不是锁死，所以图鉴解锁等"永久进度"不会被跪求刷出来。
  ⚠️ 这道折减与上面那条刷新守卫是**两道独立的闸**，别合并成一条判据。
- ★ **S4 之后没有「钱包 / 局内筹码」两个口袋了**：只有**一个余额**。
  「一局」= 把手头的余额投到见底为止，所以「收工把桌上筹码回存钱包」这笔转账**不存在了**
  （`economy` 的恒等式随之从「钱包守恒」改成**终身账守恒**，见下）。
  仍然要防的是同一个循环：「跪求 → 刷新 → 白拿起始余额」。
  守卫现在在 `SaveStore` 的加载分支里，条件比旧版**多两条**：
  `balance <= 0 且没有历史局 且没有跪求记录 且没有欠款 且 beggedTotal === 0` 才允许重置
  （`src/systems/SaveStore.ts:531-540`）。
  合并账户之后余额里可能正含着刚跪来的那笔钱，所以**只看「没跪求过历史」不够**，
  还要求本次存档里 `beggedTotal` 为 0；欠着钱的人更不能靠刷新白拿（S2 那条）。
  用例面（`tests/save-migration.spec.ts`）：反例两条 —— `debt > 0` 与 `beggedTotal > 0` ——
  外加一条**正对照**（把 `beggedTotal` 拿掉必须放行重置），没有正对照的话
  "不许重置"那两条会在重置逻辑整个坏掉时一起假绿。
  ⚠️ `beggedTotal` 那条与正对照是 10-01 新写的，**还没跑过**（当时 S6 批在飞，不能起浏览器抢 CPU）；
  跑法与状态记在计划的收尾清单里。

期望值是**故意做成负的**：庄家终会赢，玩家的本事体现在「能把入场筹码撑多久」。
设计目标是「一条命 60~90 投」。

## 界面（HUD）

- **一块语言**：HUD 的面板是**不透明深色 + 2px 双色描边 + 圆角 2px**，不用 `backdrop-filter` 玻璃模糊 ——
  像素机柜与磨砂玻璃是两种语言，并排就会出现"屏幕上贴了一条别的东西"。定义收在 `styles.css` 的
  `--hud-face / --hud-edge / --hud-edge-lo` 三个 token，改一处就全改。
- **余额只有一个读数**：宽视口（≥900px）下 DOM 的 `#resource-readout` 收起，余额的唯一真源是招牌屏；
  窄视口反向保留 DOM 读数（小屏上招牌屏被压小，像素字看不清）。
- **顶部条让出招牌屏**：出厂机位下招牌屏投到屏幕空间占 `x 406~874 / y 7~103`，
  顶部条用 `--marquee-clearance`（104px）避开它。⚠️ 这是**量出来的常数**而不是投影锚定 ——
  视口或机位一变就会失准，锚定做法（HUD 跟着投影走）在计划里被明确推到另一轮。
  实测两个视口都不重叠：`1280×720` 屏 `y 7~103` / 条 `y 116~190`；`390×844` 屏 `y 149~220` / 条 `y 8~71`。
- **禁用的按钮不减透明度**：灰阶 + 收 glow，不做 `opacity: 0.55`（半透明读作"还没加载完"，灰掉才读作"不能按"）。
- **可读下限 11px**：`#hud` 内任何可见文本的 computed `font-size` 不许低于 `--text-min`（11px）。
  判据是 camera 段的 **G-字号**。
- **机关剩余次数是计数灯**：抓斗那一格画方块灯（亮 = 还能用，暗 = 已用掉），不是"剩 2 次"这种小字。
  总位数取 `max(表的上限, 当前剩余)` —— 「机关充能」能把次数加到超过开局档位，
  固定按表画会**少亮一盏**，而少亮一盏是说谎的显示（G-计数灯 就是抓到过一次才写成这条的）。
  ⚠️ 计划原话是"成本/次数改计数灯"，落地只做了**次数**那一半：**成本是价格不是余量**，
  "花 2 筹码"画成两盏灯读起来跟"还剩 2 次"一模一样 ⇒ 只会多一套要查表的暗号。
  价格仍走 DOM 文本，但吃同一条 11px 下限（G-字号），所以 0.6rem 那批 `<small>` 确实被删干净了。
- **候选卡的图案走像素字**：`render/pixelText.ts` 把"小画布 fillText + 整数倍放大"抽成通用小件，
  三选一的徽章用它画（系统字体就够，不需要字体资产）。名字与价格仍是 DOM 文本 ——
  无障碍树与判据都要读得到字，全画布等于把信息藏进像素里。
- **机关行的名字是铭牌**（Stage 3b 的最后一格）：扫板 / 抓斗 / 后装填 / 加注 四个名字改由 `pixelText`
  画成像素字，"像素机柜 + 抗锯齿正文"两种语言并排的那半就此合上。文案与颜色都**从 DOM 现读**
  （`span.textContent` + computed `color`，这里不抄第二份），而 DOM 那段文本**不删**、只收进
  `.pixel-hidden` —— 画布里的字机器读不到，删掉等于把无障碍一起丢掉。判据是 camera 段的 **G-铭牌**
  （三条一起断：有画布、数得出墨、文本仍在且是收起态），变异臂 `UI_NEG_ARM=nameplate` 摘掉 4 枚画布能让它单独红。
  ⚠️ **铭牌只在 ≥900px 出现**：窄视口回到 DOM 文本。加铭牌那版在 390×844 下把机关行顶出屏幕
  （实测 `#drop-button` 右边到 437），accept ⑭ 当场红了 —— 屏放不下时可读性优先于统一语言，
  这与余额读数的取舍是同一条规则，不是漏做。⑭ 现在也会直接说出是哪颗按钮出了界。
- **圆角收到 2px 以内**（计划里"圆角 8~14px → 0~2px"那一格）：动手前先用浏览器**现读**了一遍，
  发现上一轮"硬边化"只改了面板，**按钮与胶囊整批漏掉** —— `#hud` 里可见元素还有 10 个角 >2px
  （机关键 9px、投币键外壳 12px、暂停/收藏 8px、`#xixi-marks`/`#mark-note`/`#combo-toast` 三枚 999px 胶囊）。
  全数收进 2px 之后，新门 **G-硬边** 又抓到一条我自己量漏的：`#status-line` 是不对称的 `0 6px 6px 0`
  —— 我第一版探针只看左上角，看不见它，所以判据改成**四个角逐一核**。
  圆形只留给 `#drop-button::before` 那顶按钮帽（伪元素不在这条的取样面里 ⇒ 白名单是空的，这条最硬）。

## 验证与测试

### 调试面板（`?debug`）

带 `?debug` 打开会挂上 lil-gui 调参面板。其中「**摄影机（角度 / 坐标）**」分组（S22）用来
摆机位并复现某张截图：

- **角度**：方位角 yaw / 俯角 pitch / 到观察点距离
- **坐标**：相机 x·y·z（观察点不动、朝向跟着变）与观察点 x·y·z（相机不动、只有朝向变）
- 「回到默认取景」= 交还给 `fitCamera()` 的自动取景

角度与坐标**不是两份数据**：真源只有 `cameraRig`（`src/render/cameraRig.ts`）里的
`position` 与 `target` 两个点，角度是 `(position − target)` 的球坐标反解，
四组控件只是同一份数据的四个视图。

★ 拖动任意一个手动控件都会把「自动取景」关掉（= 交出机位所有权）——
不这样的话，之后改 FOV 或改窗口尺寸会被 `fitCamera()` 弹回默认视角。

### 画面分辨率与像素风（`?pixel`）

默认档是**原生分辨率 + 平滑采样**（`src/render/PixelScale.ts` 的 `PIXEL_SCALE_DEFAULTS`）。
块状像素风改成显式通道，两个旋钮**正交**：

| 旋钮 | 管什么 | 关掉会怎样 |
| --- | --- | --- |
| `targetHeight` / `upscale`（面板「像素目标高度」/ `?pixel=N`） | 内部分辨率 = CSS 尺寸 ÷ 整数倍率 | 回到按视口推导 |
| `pixelated`（面板「像素化」） | 放大方式：最近邻 or 平滑 | 只是不再块状，**倍率不变** |

- `?pixel=2/3/4` = 显式倍率 **并**打开最近邻（写数字的意图是「看像素风」，只降分辨率不换采样是半条路径）。
- `?pixel=off` = 原生 + 平滑，等价于默认档，留着纯粹为了 A/B 对照时一眼可见。
- 画质分档（`PerformanceGovernor`）只动 `targetHeight`，所以低配机上的表现是**轻微模糊**而不是方块；
  ⚠️ 玩家能不能受住"被自动降档"是另一件事：暂停面板里有一颗**「画质：自动 / 已锁定」**按钮
  （#48，10-01 用户点名「不要切画质啊」之后加的）。锁上走的是同一个 `freeze()`，
  **不是第二套换挡逻辑**，锁不写进存档（刷新就回到自动），解锁时滞回计数会被清零，
  免得"解锁瞬间立刻补一次换档"。自动档本身仍然开着 —— 它救的是低端设备，不该被锁功能废掉；
  想让降档变「更方块」就同时把 `pixelated` 打开。
- 倍率曾和 `pixelated` 绑在一起：关掉像素化会把倍率吞回 1，于是默认档下降档**静默不省任何东西**。
  这条被 `verify-game.mjs perf` 的「关最近邻后倍率仍是 2」钉住，别再合回去。

## 数值标定

这个项目的物理与经济参数**都是扫出来的，不是拍脑袋定的**，
`src/game/constants.ts` 里每个关键常量都带着完整的实测表格和取舍理由。举两个例子：

**`PHYSICS.erp = 0.8` —— 这台机器上最重要的一个常量。**
它决定币堆能不能站住。Rapier 默认值 0.2 在这个规模下太软：318 枚币压上去，
位置修正打不过载荷，整堆会**沉进地板并就此睡着**（实测 300 枚币床里 299 枚币心在地板以下，
同格层间距从 0.0212 被压到 0.0084 —— 盘面高度被压掉 40%）。单变量扫描：

```
erp  0.20 → 299 枚沉入 / 最低币心 −0.0250   ← Rapier 默认，盘面被压穿
erp  0.60 →  53 枚沉入 / 0.0060
erp  0.70 →   0 枚沉入 / 0.0080             ← 阈值在 0.6~0.7 之间
erp  0.80 →   0 枚沉入 / 0.0080             ← 采用，留余量
```

同一批实验里把求解器迭代次数翻 4 倍只把沉入枚数从 299 降到 293 ——
**瓶颈是刚度，不是迭代次数**。

**`TABLE.pusherTravel = 0.36` —— 推板行程，经过三次重扫。**
行程拉长会把整张币床当刚体推走（0.84 米时实测 8.4 枚/循环、单循环最多 106 枚），
但行程太短又会憋死（0.20 米时最长空档 17 个循环）。
而且它不能只按「憋不憋死」选 —— **推进率是经济的输入**：
规定在 0.36 米（1.087 枚/循环）而不是更保守的 0.30 米，是因为后者会让单局只剩 40 投，
低于「一条命 60~90 投」的设计目标。

**`ENDLESS.bronzePayoutChance = 0.18` —— 全机唯一的主水龙头。**
它不能被代数反推出来，因为「越线/投币」这个分母**自己依赖局长**：
局越短 → 垫底库存还没被推出来 → 越线比越低 → 回收越低 → 局更短，是个自我强化的循环。
最终用 `perDrop ≈ 0.564 + 0.168·ln L` 拟合三个点、解自洽平衡得到 0.18，
再用 `ECON_RUNS=200` 的批量跑核对。实测五局：局长 48~74 投、×1 档回收率 0.46~0.80。

> 结论：**改推进率（推板行程 / 币床几何 / 币堆刚度）之后必须重标经济**，
> 而且必须按自洽平衡解，不能拿单一局长的读数当常数用。

## 说明

- 全部数值与断言都是**可复现**的：随机数走游戏 RNG，测试通过 hook 注入种子
- 经济模块是**纯函数**：不持有状态、不碰物理与渲染，随机数由调用方传入
- 静态资源（`src/*.mp3`）随仓库分发
