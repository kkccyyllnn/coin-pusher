## 0. 从 v3 继承的纪律（每条阶段验收都适用）

1. **一次只改一个变量、改完重新量。** 阶段内部也成立：一个大改造拆成可独立复测的小步。
2. **判据不写第二份公式**——数值判据一律枚举调用引擎函数（`crossingReturn` / `betTiers` /  
   以及本计划新增的 slot 映射函数）收成集合，不在测试里手写展开。（PLAN-v3 §6.13）
3. **结构性修复后，被恒真化的判据要主动降级**——修复让旧断言必然成立时，  
   换一条能继续观测同一缺陷的断言，否则「修好了问题，也修没了证据」。（PLAN-v3 §6.15）
4. **概率性断言按频率测**：`--repeat-each` 取频率，单跑绿不算数。
5. **两条验证链一起跑**：`verify-game.mjs`（引擎状态）+ `npx playwright test`（真实浏览器帧节奏）。  
   只跑一条不算收口。
6. **物理是经济的输入**：任何动物理/动推进率的事，必须重跑 `pace` + `economy` 并记录读数。
7. **每阶段收尾跑全量**：九个模式 → `tsc --noEmit` → `npm run build` → `playwright` 全绿，  
   实测读数写回本文件对应章节。
8. **构造测试状态分清「身份」与「壳」**：依赖本局累计值的路径用 `forceRuin()` 一类  
   不重开局的钩子，不用 `setState`。（PLAN-v3 §6.13）
9. **每条机制至少留一条冷路径 + 断言绝对数**（算式写出来），不要只断言增量。（PLAN-v3 §7-9）

## 3. P3 · InstancedMesh 渲染改造

### 3.1 现状与动机

- `CoinPool` 每枚币一个 `THREE.Mesh`（318 枚活跃 + 预留到 `COIN.budget = 500` 的对象池），  
  共享一份 `CylinderGeometry`、按 kind 分 4 份材质——**已经是天然的分组结构**。
- 每帧 `Coin.sync()` 逐枚 `updateMatrix`；318 枚 × 阴影 = drawcall 大头。
- 这步是纯技术债，不改任何玩法/物理。**它是 P4~P7 的前置**：演出要在满盘上加更多  
  可见实体（装置、塔、滚筒），先把每枚币一个 drawcall 的底数降下来。

### 3.2 设计

1. **先测基线**：改前跑 `perf` 模式，记录 `renderer.info.render.calls` / `triangles` /  
   帧时间。已知坑：无头环境顶 60 FPS，**对比的是 drawcall 数，不是帧率**（PLAN-v3 §7）。
2. `CoinPool` 改为 **4 组 `InstancedMesh`**（bronze / pattern / payout / bounty），  
   每组容量 = `COIN.budget`。`Coin` 类保留物理体与全部状态  
   （`kind / active / playerDropped / betMul / onDeck` …），**渲染从「持有一个 Mesh」  
   变成「持有一个 (组, index) 引用」**；`sync()` 写 `instanceMatrix` 而不是 `updateMatrix`。
3. **kind 变化 = 换组**（现只有 `spawn` 时定 kind，机制上预留：老虎机/宝箱若注入指定  
   币种的币，走同一接口）。
4. **换肤**：`applyCoinSkin` 照旧重建 4 份材质、赋给 4 组，旧材质显式 `dispose`（现状已是）。
5. **阴影**：按 `InstancedMesh` 组开关 `castShadow`，画质分档逻辑不变  
   （`PerformanceGovernor` 只调 DPR/阴影，见 MEMORY）。
6. **先清点直接引用 `coin.mesh` 的地方**，全部改成走抽象层——源码里已看到：  
   `Game.ts` 的 `recordFallOff`（约 1552 行，`entry.coin.mesh` 做记录键）、  
   `penetrationReport`（约 1610 行，按 mesh 对上报穿透对）。  
   **这是本阶段最容易漏的一步，先 grep 再动手。**

### 3.3 红线

- 渲染层**只读**物理数据。`fixedUpdate`、推板、`Coin` 的物理接口一行不动。
- 不改 `Coin.budget`、不动对象池大小语义。
- 改完全量复测（九模式 + playwright）；重点看 `physics` ②（推板节拍跟得上实时）——  
  它是帧时间的哨兵；以及 `visual.spec.ts` 的渲染断言（画面非空白、机台可见）。

### 3.4 验收（全部通过，2026-09-22）

- [x] `renderer.info.render.calls` 显著下降并写入 PLAN-v4（目标量级：**< 50**，改前基线对比）

**实测读数**

  三角形 23660 → 23588 基本持平；各画质档/CPU 降速组合均 60 FPS（瓶颈本就不在 CPU）。

### 3.5 全量复测抓到的第四个真实缺陷：侧壁薄墙被币堆挤穿（已修）

P3 自身是纯渲染改造，但全量复测（纪律 5：两条链一起跑）在 mobile-safari 上  
抓到 `bot-playtest:68` 一次 `anomalies=1`。按纪律 4 用 `--repeat-each=16` 复现，  
第 14 次抓到现场样本：

```
bronze  x=1.317  y=0.412  z=0.812  vx=1.38  vy=-0.51  vz=-0.40  speed=1.53
```

- **判读**：侧逃（|x|>1.3），但速度只有 1.53 米/秒——不是 §6.15 的能量弹射，  
  速度护栏（8 米/秒）天然管不到。`vx=1.38 ≈ erp 0.8 × 穿透 0.03 / dt(1/60) = 1.44`：  
  币堆侧向压力把币**低速挤进** 0.06 米薄侧壁，币心越过墙体中面后，  
  Rapier 的「最小穿透方向」解算翻面，把币朝**机外**踢出（erp 顺手补了一脚）。
- **修复**：侧壁（护栏段 + 围板段）碰撞体厚度 0.06 → **0.24 米，只向外侧加**  
  （内侧面 x=±0.80 不动，合法接触零变化）。翻面需币心深入 0.134 米  
  ≈ 10 倍币半径，币堆压力做不到。验证：修复后 `--repeat-each=16` 全 0 异常  
  （修复前约 1/24）。
- **审计备注**：地板（0.10 米）与后墙同理偏薄，但 24+ 局无逃逸证据——不动，  
  留给 P8 统一审计（纪律 1：一次一个变量）。
- **测试基建顺手补强**：`bot-playtest` 三处 `anomalies===0` 断言改为  
  `expectNoAnomalies()`，失败时自动转储 `anomalySamples`——下次再红自带现场。

## 4. P4 · 投放演出系统（ShowDirector + 三装置）

### 4.1 定位（拍板决策 5 的原文）

> 几何投放演出：程序化几何装置。用户原话：「桌面中心突然伸出一个圆柱，回缩留下金币塔。」

**演出 ≠ 视觉假币**。演出结束时留在盘面上的必须是**真实物理币**  
（走 `CoinPool.acquire() + spawn()`）——否则违反两条 v3 硬约束：  
「结算只由币是否越线决定」（PLAN-v3 §2.1 决策 9 赌局定位）与「不静默删币/造币」。

### 4.2 ShowDirector

- 新建 `src/systems/ShowDirector.ts`：演出请求的**统一入口与调度**。  
  接口名已经被预定：`economy.ts:67` 写着  
  「P6 会在这里加 diamond（固定 25）与 chest（0，改由 ShowDirector 派发投放演出）」。
- 职责：接收请求（`request('chest' | 'tower' | 'fountain' | 'gate', opts)`）→  
  检查预算 → 编排装置动画（纯视觉，THREE 几何体）→ 在关键帧 `spawn` 真币 → 回报结果。
- **预算检查是第一公民**：注入要吃 `COIN.budget` 余量。余量不足时**演出降级**  
  （比如塔少几层）或**明确拒绝并给玩家反馈**——绝不静默少发  
  （MEMORY：`acquire()` 静默返回 null 是历史坑）。
- 演出**不暂停结算**：真实物理世界不停，演出注入的币从 spawn 那一刻起参与一切规则  
  （越线返值、异常检测、速度护栏一视同仁）。

### 4.3 三装置（草案，第 2、3 个待拍板 #4）

| 装置           | 形态                        | 注入                          | 备注                  |
| ------------ | ------------------------- | --------------------------- | ------------------- |
| **A · 圆柱币塔** | 台底（币床中心）升起一根圆柱，顶出一座真币塔后回缩 | 一座塔（层数随预算弹性，默认 3~5 层 × 4 枚） | 用户原话的形态             |
| **B · 喷泉**   | 背板前缘向盘面均匀抛出一弧真币           | 8~12 枚散布                    | 用真抛射，落点交给物理         |
| **C · 闸门落币** | 背板下方开一条缝，滚出一排真币到台面        | 6~8 枚一排                     | 从台面后区补库存，视觉上是「庄家补货」 |

三装置共用：装置几何体（THREE 原生几何拼装，无外部模型）、spawn 预算检查、  
演出完成回调。**装置是「几何演出风格」的母版**——P7 的机关演出从这里学语言。

### 4.4 红线

- 任何演出注入的币**必须能在 `coins()` 里逐枚查到**（判据：注入前后活跃币数差 = 请求数）。
- 演出期间三账本恒等式照旧成立（注入是盘面事件，不是账本事件）。
- 装置动画不碰 `fixedUpdate`；动画帧回调里只做视觉 + 到点 spawn。

### 4.5 验收（全部通过，2026-09-22）

- [x] 新验证模式 `show`：请求圆柱币塔 → 塔**全是真币**、逐枚可查、预算正确扣减
- [x] 预算打满后请求 → **拒绝有明确反馈**（不是静默无事发生）
- [x] 演出中连续结算不丢账：`economy` 恒等式检查在演出期间抽查成立
- [x] 全量复测绿

**落地结构**

- `src/systems/ShowDirector.ts`：`request('chest'|'tower'|'fountain'|'gate', {count?, kind?, x?})`  
  → `{ok, promised, downgraded, reason?}`；FIFO 队列（上限 4）一次一场；  
  `busy/queued/activeId` 进诊断快照（P7「演出期间收尾计时暂停」将读 `busy`）。
- 三装置：A 圆柱币塔（默认 4 层 16 枚）、B 喷泉（3 波真抛射 10 枚，vy ≤ 2.2  
  在合法上限内）、C 闸门落币（逐枚滚到推板顶面尾部输送带 7 枚）；  
  `chest` 注册为紧凑塔（8 枚）——接口就位，P6 接越线触发。
- 遥测新增 `showEvents`（registered / completed / refused 三态）；  
  测试钩子 `showRequest(id, opts)`。降动效压缩时间轴但**不少发一枚**。

**判据口径修正（首跑 7/10 暴露，已修并记入纪律库）**

- 「注入前后活跃币数差 = 请求数」在满盘上是**假判据**：注入必然 Cascading，  
  被挤的币会合法越线（实测塔 +2、喷泉 +2）。正确算式：  
  **活跃差 + 结算差 = 承诺数**（注入币只有「留盘 / 合法结算」两条去路）。
- 两态之「登记」必须等一帧再读诊断（快照逐帧发布，立刻读会拿到请求前的旧帧）。

**实测读数**

- `show` 模式 10/10：塔 / 喷泉 / 闸门全真币交付；两态事件齐（registered 时币未动、
  completed 实发 = 承诺）；降级路径实测（按实有余量承诺，HUD 告知）；
  池底拒绝（reason + refused 事件 + 盘面不变）；演出交付后三账本恒等成立。
- 全量复测：九模式 + `show` 全绿，`tsc` 0 错、`build` 干净、playwright 42/42。

> **P5 后修订（2026-09-22）**：本节读数记的是 P4 收口时的量级（塔 16 / 泉 10）。
> P5 引入 XIXI 奖励水源后，**演出量级被免费币预算红线重定**（现档 塔 1 / 泉 1，
> 详见 §5.7），`marks` 模式被 `xixi` 模式替换。P4 的装置形态、两态事件、预算语义

## 5. P5 · XIXI 集章 + 背板老虎机（替换三路集章）

### 5.1 现状（要被替换的东西）

- `RunState.marks`：3 路通道印记；币掉到币床（`p.y < channel.registerY`，  
  `channel.edge = ±0.27` 分三路）→ `markChannel(lane)`；三路全亮 →  
  `boostCharges + 1`（加力来源）。**这是加力目前唯一的来源**——拍板项 #1 的根源。
- 被替换后，`marks / markChannel / channelMarksEnabled` 与 HUD 三路印记一并拆除。  
  **保留 `channel.registerY` 的判定语义**（「真的掉到币床上才算」），XIXI 沿用。

### 5.2 XIXI 四槽

- 槽位：X · I · X · I 四段，覆盖 `drop.halfLane = 0.68` 的落点区间，  
  每段 0.34 米：`[-0.68,-0.34)=X₁`、`[-0.34,0)=I₁`、`[0,0.34)=X₂`、`[0.34,0.68]=I₂`。
- **点亮 = 币落到币床那一刻的 x**（拍板项 #2 默认物理落点）：  
  只有玩家主动投入的币（`playerDropped`）且掉到床上才登记——  
  复用 `Game.processOutcomes` 里现在的通道登记点。

### 5.7 P5 最大的发现：免费币水源是「点火」的触发器（P8 必须从这里接）

XIXI 的奖励是「演出 + 真币」，而真币经越线会换回筹码——**它是一条新的筹码水源**，
`economy` 与 `endless` 会立刻把符号漂移变成红灯。四轮实测把量级夹了出来：

| 档位（塔/泉枚数 + 权重） | 水量（枚/投） | 节奏机器人（160 投上限） |
| --- | --- | --- |
| 16 / 10（P4 草案） | ~0.90 | 不破产（快投 600 秒 1191 投、筹码 20→495） |
| 8 / 4 | ~0.38 | 160 投仍剩 66 筹码（越线/投币 1.29） |
| 6 / 4 | ~0.32 | 240 投不死（越线/投币 1.81） |
| 4 / 3 | ~0.22 | 约 1/3 局次**点火**（158~240 投不终局，回收 1.06） |
| 1 / 1 + 15/15/70 | ~0.027 | 仍会点火（1/8 局次，159 投不终局） |
| **1 / 1 + 5/5/90（现档）** | ~0.009 | ✓（endless 27~37 投破产；economy 51/78 投，回收 0.75/0.74） |
| **0 / 0 + 0/0/100（隔离实验）** | 0 | ✓ 3/3（24~48 投破产，回收 0.65~0.7） |

**机理（隔离实验确认）**：免费币让盘面变肥 → 垮塌更大 → **排水后的盘面**
（币都挤在得分线附近）越线/投币升到 1.2+、回收率爬到 1.0 以上 → 局永不结束。
这是**阈值型自增强回路**，不是尾部分布：只要每投注入 0.03 枚就足以把
「20 筹码能撑到的投数」推过阈值（从 ~70 投推到 ~100 投，刚好够盘面进入热区）。
把金币奖权重归零后 endless **3/3 全绿**——**水源就是触发器**，与量级大小不成线性。

**结论与现档取舍**：

- 金币奖压到「稀有头奖」量级（tower/fountain 各 5% 权重，1 枚），加力占 90%
  （**只有加力是不往盘面加质量的奖励**）；`xixi.ts` 里留了
  `FAUCET_BUDGET_PER_DROP = 0.04` 作为预算红线注释。
- 代价：正常一局（~60 投）里塔/泉演出**几乎不会自然触发**——它们的可验证性
  由 `xixi`/`show` 模式的**强制摇奖钩子**保证（`xixiSpin('tower'|'fountain')`），
  结构完整、只是经济权重待 P8 放开。

**P8 的活（按优先级）**：① 让基础经济带上缓冲——把排水盘的回收率压到 ~0.9 以下
（现档在阈值上，任何水源都会点火）；② 再决定金币奖的权重/枚数，把塔/泉放回
「看得见的奖励」；③ 若要让塔/泉回到阵型规模（3~4 枚），必须同时动 ①——
**两者是耦合的**，这也是 §6.12 把标定推迟到 P8 的原因在本阶段被实测印证。

### 9.1 开局没有起始筹码 = 状态机死锁（真 bug，不是「没发筹码」）

钱包被反复刷新扣空 → `buyIn()` 返回 0 → `RunState` 停在 `phase='ready', chips=0`：

```
acceptingDrops = (ready||playing) && chips > 0   → false   （投不了币）
沉降分支       = phase==='playing' && chips <= 0   → 永不进入
showRuin()     = 只由「沉降走完」/ forceRuin 触发  → 永不触发
```
而**跪求按钮挂在破产弹窗里** → 玩家既不能投币也不能跪求，画面彻底无响应。

修复走**既有沉降机制**（`beginPlay` → `enterRuinSettle` → `showRuin`），
因为 `RunState.revive()` 只在 `phase === 'drainOut'` 时生效 —— 只弹窗不绕这一圈，
`grantBeg` 的 `resumed` 会静默返回 false、阶段永远停在 `ready`。

**新增判据（`endless` 模式）**：
```

  — 买入 0，筹码 0，阶段 drainOut，沉降原因 exhausted，破产窗 true
钱包见底后跪求：赏赐到账、本局被拉回 playing、能真的投出币
  — 跪求 true，筹码 30，阶段 playing，破产窗 false，投币被接受 true
```
构造用 `setWallet(0)` 钩子（一步到位），不靠反复 `startRun` 把 200 扣完。

**★★ S1 实际踩到的坑：图集「切格顺序」静默错位（2026-09-24）**

原方案照抄 `pixel-cube-v3.html` 里那段 legend 的**列举顺序**

实际图集从左到右是：**胡萝卜 · 宝箱 · 叉 · 黄瓜 · 桃 · 钻石**。

1. **构建期底色守卫**：`build-icons.mjs` 里 `EXPECTED_BACKGROUND` 钉死每格底色，

**★★ S7 实际踩到的坑：排水口吃掉「开局就坐在洞上」的 4 枚预置币（2026-09-24）**

`layout` / `physics` 一起报 `activeCoins = 314 / 318`，异常 0、币种合计 318、币池预算够
—— **所有计数判据都是绿的**，只有「实际生成枚数与配置一致」和「静置 10 秒不丢币」红。

根因：`BED_FRONT` / `BED_EDGE` 的网格含 `x = ±0.72` 一列，而 `z = 1.1` 正落在
`DRAIN.zMin..zMax`（0.98~1.15）里。洞的 footprint 没有地板碰撞体，于是
**`BED_FRONT` 两层 × 2 列 = 4 枚**预置币第一帧就掉出机柜。差额精确等于 4。

处置（**修配置，不放宽判据**）：

1. 新增派生常量 `DRAIN_FOOTPRINT`（洞的平面占地，真源只有一个）与
   `DRAIN_CLEARANCES`（内边界各退 `MAX_JITTER`，因为网格存的是**未加抖动**的格点，
   而物理拿到的是加过抖动的坐标——不退这一点点，贴着洞边的那一列会「自检过、物理掉」）；
2. `ENDLESS_SPEC.clearances` 加上 `...DRAIN_CLEARANCES`，318 → 314；
3. `assertLayoutValid` 新增一条自检：**币床上不得有币坐在排水口上**。
   它兜的是 `towers` —— `clearances` 只过滤区域网格，**塔不经过它**；
4. `layout` 判据一字未改，直接转绿。

> 这条与 S1 同源：**「配置写错」和「物理跑错」都表现为一个变小的计数**，
> 而计数类判据（币种合计 / 异常 / 预算）盖不住它。区别是 S1 错在**名字↔像素**，
> 这里错在**几何↔几何**——洞的位置在两个地方各写了一份（`DRAIN` 的判据 + `TableBuilder`
> 的地板块），第三处需要知道「哪里是洞」时就必须从 `DRAIN_FOOTPRINT` 派生。

**★★ S8 实际踩到的坑：台面输送的例外以前借用 `playerDropped` 表达（2026-09-24）**

`refill` 的第一条行为判据（币床枚数要回升）直接红：掏空到 120 枚 → 闸门承诺 7 枚 →
`spawned = 7`、`activeCoins` 照涨 7、`show` 模式全绿 —— **但币床一枚都没涨**。

根因：`GateShow` 把币吐到**推板顶面**（`y = pusherTopY + 0.06`、`z = backZ + 0.05`），
靠台面输送带送过前缘才落进币床。而输送带那行写的是

```ts
if (!coin.playerDropped) return;   // 只有玩家投下的币才吃输送
```

在「只有预置币 + 玩家币」的年代这句**恰好等价**于「预置币不吃输送」。P10 把 `gate`
接成自动补币装置之后就不等价了：闸门币既不是预置、也不是玩家投的，于是**不吃输送**，
初速 0.8 m/s 被摩擦在 5 厘米内吃掉，7 枚币**永久停在推板顶面**。
`gate` 在 P10 之前**全库无调用方**（§10.2 已记），所以这个洞一直没被踩到。

处置：

1. 把那个例外**显式命名**：新增 `Coin.preset`（只有 `Game.startRun` 摆盘时置 true），
   输送带改成 `if (coin.preset) return;` —— 语义变成「**运行期注入的币一律要吃输送**」；
2. 新增诊断 `deckCoins`（停在推板顶面的活跃币数），与输送**共用同一份判据**
   （抽出 `Game.isOnDeck`，不写第二遍，所以它不受降动效跳过 `fixedUpdate` 的影响）；
3. `refill` 模式判据收紧成两条：**多数补货币落进币床** + **推板顶面不积压**。

实测（修复后）：币床 120 → 峰值 **125**（7 枚中 5 枚到账，2 枚在途中被下水道吃掉，
属设计内损耗）；推板顶面 18 → 峰值 24（7 枚在途）→ **末值 18**。

> 教训：**「借用一个语义相近的布尔量」是会过期的**。`playerDropped` 在 P2 写那行时
> 确实等价于「不是预置币」，但它是**身份**（谁能点亮 XIXI），不是**行为**（谁该吃输送）。
> 一旦出现第三类币（运行期注入、非玩家），两者就分叉，而分叉的后果是**静默失效**：
> 币数一切正常，只是永远到不了该到的地方。凡是「拿 A 的字段当 B 的条件」，
> 都要问一句「A 还能不能唯一确定 B」。

**补记：S8 为什么不需要改 `visual.spec.ts` 的 `activeCoins === spec.coins`**

§10.4 原先预告这条必红。实际落地时**没有红**，因为补币被 `phase === 'playing'` 挡住，
而 `visual.spec.ts` 的 5 处 `activeCoins === spec.coins`（93 / 183 / 196 / 224 / 356）
**全部在 `ready` 态**（首帧 / 静置 2.5 秒 / 重复开局 / 破产重开后），
`ready` 阶段补币根本不触发。

这比「改成开局帧快照 + 两态判据」更好：**判据没被削弱，是机制被设计成不破坏它**。
两态判据只在真的无法避免时才用（例如补币发生在 `playing` 中途——
那种情况下 `activeCoins` 本来就不该恒等于预置数）。

**★★ S10 实际踩到的坑之一：判据的「期望值」本身写错了（2026-09-24）**

`feedback` 模式的第 ① 条判据（枚举 `crossingFeedback()` 的边界点）第一版 **7 例中 5 例 ✗**：

```
筹码 24 / 连落 1 / 热区 否 → 期望 normal/—/无高潮，实际 normal/—/kind ✗
```

根因**不在实现**，而在判据：我先把「无高潮」写成了期望，之后才发现
**钻石自带 `climax: { strength: 1, tone: 'blue' }`、宝箱自带 `gold`、大赏币自带 `gold`**
——只有 `bronze` 与 `bounty` 是 `climax: null`。

处置（**不放宽断言**）：**把币种变成判据的一维** ——
`bronze` 验「没有就是没有」，`diamond` 验「阈值之前走 `blue`、到了阈值被 `white` 接管」。
改完 10/10 全绿。

> 教训：**判据里的「期望值」是第二份真源**。写它之前必须先去读引擎的单一真源
> （这里是 `kindSpec(kind).climax`），否则「实现对了、判据错了」会以同样的红色呈现，
> 而人第一反应总是去查实现。这与 S1 的「名字↔像素」、S7 的「几何↔几何」同源：
> **凡是判据里出现了第二份数据，就要问它跟真源是不是同一份。**

**★★ S10 实际踩到的坑之二：新增一个网格 = 新增一份着色器程序变体（2026-09-24）**

洞口闪光第一版做成独立 `InstancedMesh`（两片发光板），`perf` 立刻报：

```

```

根因：`InstancedMesh` + **无贴图** + `SD_DETAIL_KIND=0` 这个 define 组合此前**不存在**，

> 教训：`perf` 里「程序数 < 材质数」判的是**共享性**，不是绝对上限。
> 但**新增一个材质族/define 组合**会实打实地多一份程序 —— 在 draw call 只剩 6 个名额、
> 程序只剩 0 个名额的当下，**「复用已存在的物件」优先于「新建一个更干净的物件」**。

### S11 物理侧标定（第 2 阶段，2026-09-24）——★ 用户的手感反馈指对了地方

用户原话：「如果有『局永不终局』的困扰，可以考虑调整硬币的物理属性，现在感觉太灵敏了，

第 1 阶段把 S11 当成纯水源标定，三轮试错都没把方差压下去（极差 16~216 投）。

（推过去滑、退回来又滑回去）→ 同一行程真正送过得分线的枚数方差极大 →
**那才是雪球局与塌陷局的成因。水源只是把噪声放大，不是噪声源。**

**改动四项**（`src/game/constants.ts` + `src/systems/TableBuilder.ts`）：

| 项 | 旧 → 新 | 管什么 |
| --- | --- | --- |
| `COIN.friction` | 0.3 → **0.5** | 币↔币 与 币↔台面（Rapier 按 **Average** 合并，单改一边只有一半效果） |
| `COIN.linearDamping` | 0.15 → **0.3** | 自由滑行段的残余滑动 |
| `COIN.angularDamping` | 0.7 → **0.9** | 消除「原地打转」（转动不产生推进，只在接触时随机还能量） |
| `floorFriction` | `{0.32, 0.02}` → **`{0.45, 0}`** | 台面；0.02 的弹性会被累积成微抖动 |

★ **`COIN.restitution` 本来就是 0，没改。**「弹性过强」的真身是 `erp = 0.8`
（求解器硬推重叠的币 ≈ 一堆硬弹簧），它同时是「求解器凭空造能量 9~13 m/s」的同源。
**这一项本轮没动** —— 动它要连带重标 `maxSpeed` 护栏，属独立改动。

### 11.3 ★ 踩到的两个坑（都是同一类：**启发式不随尺寸放大**）

**坑 1 · 塔基保留区写死 0.20 × 0.16**

`BED_FRONT` 最靠后的一行（`z = 0.81`）到塔角币的实距在原尺寸下是 **0.1327 ≥ 0.1176**（侥幸合法），
判据随币径涨到 ×1.1 的 **0.1294** 之后就翻车了：`0.16 × 1.1 = 0.176 < 0.19`，
那一行**没被保留**，开局直接抛

```
盘面重叠：(0.434, 0.809) 与 (0.407, 0.687) 间距 0.125
```

修法是让保留区**不小于严格下界**：`half = offset + spacing`（`offset` = 塔角币离塔心，
`spacing` = 实距判据）。证明：盒子外的点必有一轴满足 `|Δ| > half`，于是到角币在该轴上
`≥ half − offset`。同时与**历史比例值**取 `max`，这样原尺寸的盘面一格不差（纪律 1）。

> ⚠️ 顺带纠正一个误判：第一版用 `corner + spacing`（`corner = offset × √2`）**过度保留**——
> 它把 `BED_FRONT` 的 `z = 0.81` 行也算进去，盘面从 314 掉到 302。严格下界是 `offset + spacing`，不是 `corner + spacing`。

**坑 2 · 两段币床各自算行距**

第一版让 `BED_BACK` / `BED_FRONT` 各自 `fitCells(zSpan, 原行数)`。原尺寸下两段行距都是 0.145，
看不出问题。×1.2 时后段 6→5 行、行距涨到 0.18125，前段 3→2 行、行距涨到 0.29，
**交界处却还是老位置**：实际间距 0.145 < 0.15312，开局抛

```
盘面重叠：(0.719, 0.667) 与 (0.724, 0.807) 间距 0.139
```

根因是「分段各自算行距」这件事本身——**两段是同一张床**。改成先算整张床的总行数与总行距，
再按行数切段（后段 = 总行数 − 前段行数）。

### 11.8 ★ §3.3（演出塔的碰撞体/重量/灯环）为什么不做

读 `TowerShow` 的几何发现**原计划的前提是错的**：
`topHeight() = 0.03 + layers × 0.028`，而 `spawnLayer(L)` 的 y = `0.03 + (L+1) × 0.028`
—— **每一层的币都落在这个圆柱体内**（层 0 在 0.058，柱顶 0.142），
币心半径 0.102 < 柱半径 0.18。所以给它加实心 kinematic 圆柱碰撞体会**把币挤飞**。

另外 `SHOW_SPECS.tower.count 16 → 36` 会把老虎机水量从 ≈0.75 抬到 ≈1.22 枚/摇奖（+63%），
而 `SHOW_SPECS` 的注释明确写着「只放大源不装汇 → 回收率被顶过 1 → 整局不终局」。

⇒ 这两件都要单独设计 + 重标经济，**不能混在视觉改动里做**。

### 11.9 ★ 方法：抓一次越线时间线，离线解经济标定

连落链 `combo_i = (Δt_i > W) ? 1 : combo_{i-1}+1` **完全由越线时间戳序列 + 窗口 W 决定**，
所以抓一次 `telemetry().scoreEvents`（含 `sincePrevious`）就能**离线**算出
任意 `W` / 闸门下的 `E[heat]`、`perCrossing`、`unit` —— **不用重跑游戏**。

本轮用它一次否掉了「收窄 `comboWindow`」这条路（3 轮 × 7 分钟 → 5 分钟）。
**必须配自检**：用引擎当前值重建连落链，要与实测 `combo` **逐条一致**（255/255 通过）。
没有自检，离线解就是一份没人验证过的第二份公式。

**离线模型的准确度**：预测单次越线期望 0.394，`economy` 实测 0.386（差 2%）。

**待办**：`economy` 的 ×1 回收 0.811 距目标 0.73 差 0.081 ——
按 S11 记下的纪律（「0.654 距 0.73 差 0.076，而 6 局噪声 ±0.1 → 追它是自欺」）
**不再追**。但要记住：**闸门这个旋钮已接近用尽** ——
perDrop 2.24 时非铜币那部分（花纹 + 返币 + 大赏）已占单次越线期望的 **57%**，
把铜币闸门从 0.09 压到 0.07 只能把 unit 从 0.865 挪到 0.797。
**以后再改推进率，要砍的是整张表，不是闸门。**

## 12. S14 · 落币口后移（2026-09-25，用户拍板）

起因（用户原话）：

> 「筹码很难触达红框区域，无法利用背板的物理碰撞把前面的币推挤出去。
> 现在都是利用惯性把推币台的币甩下去的，我需要你给我一些建议，看看这个情况怎么优化比较好」

### 12.1 诊断：那条链物理上不成立

**「币堆到背板上、靠背板把前面的币挤出去」做不到。** 台面上的币是**骑在推板顶面上**的
—— 它们和推板一起动。背板是一面固定墙，对币只能「挡」，做不了「推」。

台面（推板顶面）有**三段推板够不到的地方**：

| 段 | z 区间 | 长度 | 为什么够不到 |
| --- | --- | --- | --- |
| **A** | `[−1.35, −1.10]` | 0.25 | 背板到预置币堆尾排之间，**一枚币都没有** |
| **B** | `[−0.28, −0.06]` | 0.22 | 台面前唇到币床后沿的落差带 |
| **C** | `[+0.20, +1.10]` | 0.90 | 推板立面最远只到 `+0.20`，币床 78% 的深度够不到 |

而落点原来在 `−0.72`（预置堆**中间**），币一落下就落在别的币的格子上、当帧被挤出去 ——
实测右落点 `x` 从 `+0.616` 被弹到 `+0.004`。**A 区因此从来没接到过币。**

```

  −1.225 − 0.05 = −1.275  <  −1.2636                   ❌ 出生即嵌进背板
```

要取正中就得同时把 `jitterZ` 压到 0.03 —— 那是**两个变量一起动**，违反纪律 1。

| `accept` ④ 跨度阈值 | 写死 `spread > 0.3` | 那是按 `conveyor = 0.85` 标定的（币被输送带 1 秒送到前唇，落点可落在整个行程任意一点）。归零后离台**只发生在回撤段** | 改成**行程的比例**：读 `coinGeometry().pusherTravel`，阈值 25% |
| `accept` ④ 等待条件 | 拿到 **4 条**离台事件就判 | 跨度本身是**样本量的函数**：实测 4 条给 0.038 米（11%）、18 条给 0.125 米（35%） | 等 **≥10 条**（上限 60 个循环） |
| `accept` ③ 落点差异 | 读「2.2 秒后停稳的 `x`」 | 脚本别处早就写着「落点 x 不能作为判据 —— 币落下时要穿过钉阵」；而落点在空台面上之后币还会以 ~15 毫米/循环横滚，2.2 秒能漂 0.3~0.46 米 | 量**落地前最后一帧**的 `x`（阈值从 `coinGeometry().restY` 派生） |
| `accept` ⓪ 钉阵探针 | 写死 `(0, 1.16, −0.72)` | 那个 `z` 就是旧落币口。落点一改探针探空，读出来的是「碰撞体半长种类数 = 0」，**红在别处** | 读 `coinGeometry().drop.z` |

另外把「落床延迟」的口径统一按**循环数**等（不能按秒等，周期会变）：
`runXixi` 的 `landingCycles` 32 → **55**，`bot-playtest` 的窗口 90 → **180 秒**。

### 12.7 ★ 一个容易看错的事实：`fallOffEvents` 只记玩家投的币

实测同一批：台面从 62 枚掉到 8 枚（**54 枚预置币离台**），而 `telemetry.fallOffEvents`
**一条事件都没有** —— 记录条件是 `wasOnDeck && !onDeck && coin.playerDropped && p.z > front`。
拿「台面枚数在掉」去推「离台事件应该有」会得出自相矛盾的读数。

### 12.8 未解决 / 留给用户的判断

- **C 区依然存在**：台面**总长**没变（只是落点后移），推板立面够不到的那 0.9 米币床还在。
  要动它得改 `pusherTravel` 或币床前移，两者都会改 `perDrop`。
- **落点不精确**：币落在空台面上之后会横滚（实测 2.2 秒漂 0.3~0.46 米，方向偏 −x）。
  这是「穿过钉阵被撞偏 + 落地姿态」的混沌结果，不是隐藏传送（贴合偏差 ≤ 0.005 米）。
- **台面压条的位置以落币口为基准**，落点再动要重新看（已加夹取保护，但会两条挤在一起）。
- **落币走廊搬进了两个演出装置的「出币位」**（闸门闸板 / 喷泉喷口）—— 详见 §12.9，这是本次改动
  唯一**需要用户拍板**的遗留：已做的那一半（闸板不再压住静置币）是零物理代价的，
  剩下那一半（下落币闪穿装置）没有局部改法。

### 12.9 ★ 落币走廊与两个演出装置重叠（本次改动的直接副作用）

**事实**：`GateShow.slotAt.z` 与 `FountainShow.nozzleAt.z` 都写死在 `TABLE.backZ + 0.10 = −1.25`（S13 为了
避开后墙内表面而定的值，那时落点在 `−0.72`，两者相距 53 厘米、互不相干）。落点搬到 `−1.20` 之后，
**落币走廊与两个装置的几何脚印重叠**：

```
落币走廊（×1.2）：x ∈ [−0.68, +0.68] × z ∈ [−1.25, −1.15]（drop.z ± jitterZ）× y ∈ [0.224, 1.45]
  其中「币的脚印」在 z 上是 [z_c − 0.072, z_c + 0.072] ⇒ 覆盖到 z ∈ [−1.322, −1.078]

闸门闸板：z ∈ [−1.268, −1.232]（深 = 币径/4）、y ∈ [0.176, 0.344]（闭闸位，高 = 币径×7/6）
  ① 闭闸位下沿 0.176 **低于静置币顶 0.224** ⇒ 币落在带里就被闸板压住
  ② 币被摩擦拖出这条带要 ~7 秒（26 毫米/循环）⇒ 玩家一在投币，**几乎每场演出的滑闸都会扫到币**
喷泉喷口：锥体（r 0.09 × h 0.2，`rotation.x = π/3`）→ z ∈ [−1.382, −1.163]、y ∈ [1.222, 1.40]
  ⇒ 落币（y 从 1.45 竖直下落、z ≈ −1.20）**正好从锥体里穿过**（~0.04 秒）
```

**已做**（零物理代价，两个装置都无碰撞体）：

- 闸板抬到静置币顶之上 → 去掉「静置币被压住 7 秒」这个**静态**穿模；
- 出币高度与 `slotAt.y` **显式解耦**（`TABLE.pusherTopY + 0.08`，数值与改前逐位相同）
  ⇒ 抬闸板**一枚币的物理读数都不动**（`show` 10/10、`perf` 19/19 复跑通过）。

**没做**（因为闸板/喷口只要还在 `z ∈ [−1.322, −1.078]` 这个 z 带里、又在落币高度之下，
下落币就必然闪穿它们 —— 抬高只是把「静态压住」换成「0.05 秒闪穿」，**治标**）：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 闸板与喷口**贴背板**：`z` 从 −1.25 退到 ≈ −1.34（闸板变成背板上的缝、锥体改成贴背板的圆风口）；**出币点保持不变**（继续解耦） | 装置「伸出来」的立体感没了；出币点离装置 20 厘米（现在 12 厘米） |
| **B** | 落点前移到 `≥ −1.11`（要求 `drop.z − jitterZ > −1.16`），同时把台面预置**尾排从 −1.10 前移**到 ≈ −0.94 腾出 A 区 | 动预置阵型 ⇒ 要重跑 `layout` / `economy` / 返值表判据 |
| **C** | 接受：只在演出期间、且只有 0.04~0.05 秒的闪穿 | 零成本，但演出时能看到币穿过装置 |

| --- | --- | --- |

### 13.2 参考模型实测（比例的唯一来源，不靠看图估）

用 Python 直接读 OBJ 顶点（`Diamond.obj` 153 顶点；`Treasure_Glow` 9,763 顶点 / 9,942 面，**高模**）：

**钻石**（归一化：总高 = 1、腰棱半径 = 1）

| 环 | 从底（× 总高） | 半径（× 腰棱半径） |
| --- | --- | --- |
| 底尖 | 0.000 | 0.002 |
| 亭部中间环 | **0.283** | **0.432** |
| 腰棱（16 边） | **0.707** | 1.000 |
| 冠部中间环 | **0.934** | **0.700** |
| 台面（8 边） | 1.000 | **0.529** |

总高 / 直径 = **0.610**。低模把 16 边腰棱降到 8 边，比例一个不动 ⇒ 仍是标准明亮式，只是切面数减半。

**宝箱**（归一化：全宽 = 1）

| 量 | 实测 | 含义 |
| --- | --- | --- |
| 总高 / 全宽 | **0.780** | |
| 腰部 `max\|z\|` | **0.333** | 箱体半深 / 全宽 |
| 底沿 `max\|z\|` | **0.373** | 比腰部宽 12% ⇒ `baseFlare` 1.12 |
| 拱盖最宽处 `max\|z\|` | **0.3775** @ y≈0.56H | ⇒ `lidOverhang` 1.126 |

**两个量不设成常量而是派生**（避免「两个数互相打架」）：

```text
拱心高 springY = 总高 − 拱半深            （拱顶正好等于总高）
body = 1 − 1.126×0.333/0.78 = 0.519        （实测 0.52 ✓）
lid  =     1.126×0.333/0.78 = 0.481        （实测 0.48 ✓）
```

⇒ 拱盖是**真半圆**（拱高 = 拱半深），不是浅圆弧顶。

### 13.3 ★ 多色方案：色板图集 + 逐面常量 UV（**不是** `vertexColors`）

造型需要 5 档色调（亮 / 中 / 深 / 暗 / 墨），天然工具是 `vertexColors`。**但这条路走不通**：

> `perf` 的判据是 **已编译程序数 ≤ 20，而改前正好是 20（顶格）**。
> `vertexColors` 会打开 three 的 `USE_COLOR` define ⇒ **必然多编译一份程序变体 → 21 → 红**。
> 这是 S10「洞口闪光」踩过的同一个坑：新增材质族 / define 组合 = 新增程序变体，
> 这不是「放宽上限」能解决的问题。

改成：**把 5 档色调画成一张竖条色板图集，每个面用常量 UV 采一格**
（`coinTexture.createCoinModelAtlas` + `coinModels.toneUv`）。

- 面内三个顶点 UV **完全相同** ⇒ UV 导数恒为 0 ⇒ 永远采 mip 0 的那一个纹素
  ⇒ 「一个面一种平色」的观感与顶点色**逐像素等价**；
- 材质的 define 集合与既有币材质**完全一致**（`USE_MAP` + `USE_GRADIENTMAP` + `SD_DETAIL_KIND=0`）
  ⇒ **程序数与 draw call 都是零增长**（实测复跑 `perf` 19/19，draw call 仍 44、程序仍 20/32）。

配套的两条纪律：

1. **`ToonMaterial.ts` 里那个 `vertexColors` 参数被撤掉了** —— 有它没用到等于留了一个陷阱。
2. **几何体按「币种」而不是按「几何体」分组**：一个币种本来就占一个 `InstancedMesh`，
   所以给 `diamond` / `chest` 各配一份几何体**不多一个 draw call**。

### 13.4 造型与五档色调的**分工**

参考模型最醒目的特征是**「浅色框架 + 深色面板」**（参考宝箱是灰白框架 + 深青蓝面板），
而不是某一种具体颜色。所以色调**不按「上亮下暗」分配，而按构件角色分配**：

| 档 | 宝箱构件 | 钻石构件 |
| --- | --- | --- |
| `light` | 框架：底裙 / 四角立柱 / 顶沿压条 / 两条拱肋 / 正面竖条 / 锁板 | 冠上带（台面下那一圈） |
| `mid` | 锁板内宝石的**台面** | 腰棱→冠中带 |
| `deep` | 面板：箱体四面 / 拱盖曲面 | 亭上带 |
| `shade` | 宝石**侧面**（切面感） | 亭下带 |
| `dark` | 搭扣 | 底尖面 |

**宝箱的造型特征清单**（每一项都必须"看得见"）：

1. 拱盖 = 沿 x 的**半圆**桶盖，两端两条**实心拱肋**（箍）；
2. **拱肋必须比拱盖曲面凸出一圈**（`lidRecess 0.90`）——齐平的话「两条箍 + 中间一块面板」
   就消失了，渲出来只是一个素圆桶；
3. 箱体是**切角矩形**棱柱（不是正八边形）：实测箱体宽:深 = 1 : 0.666，正八边形做不出这个长宽比；
4. **四角立柱沿对角向外推**（`postProud`）——不推则柱子的外角**正好等于**切角前的矩形角，
   整根柱子落在轮廓里面，24 个面一个都看不见；
5. 底裙（`baseFlare` 1.12）+ 顶沿压条（`rimOverhang` 1.03）；
6. 正面中央竖条 + **六边锁板** + 宝石 + 搭扣。

**刻意不做**：侧面的提环。它在 x 上比箱体宽出 0.13，会突破「模型不超出碰撞体」。

### 13.5 尺寸与碰撞体

| 件 | 外接直径 | 包围盒（宽 × 深） | 总高 | 相对币厚 | 碰撞体 |
| --- | --- | --- | --- | --- | --- |
| 钻石 | **124.0 mm** | 124 × 124 | **75.6 mm** | 3.15 × | 圆柱 r 62.0 × h 75.6 |
| 宝箱 | **132.0 mm** | 118 × 95 | **82.1 mm** | 3.42 × | 长方体 117.8 × 82.1 × 94.7 |
| 普通币（基准） | 144.0 mm | 144 × 144 | 24.0 mm | 1.00 × | 圆柱 r 72.0 × h 24.0 |

- **尺寸一律从币径派生**（`MODEL_DIAMETER_RATIO`），不写死毫米 —— `?coin=` 一换就失真。
- 「外接直径」= **最远顶点到中轴的距离 × 2**，**不是包围盒对角线**。
  第一版拿对角线当外接直径，钻石报出 1.2178（实际 0.8611）—— 包围盒角可能根本不是模型的点。

- **碰撞体从几何体的 AABB 反算**（`coinColliderSpec`），不手抄数字 ⇒
  「模型 ≤ 碰撞体」这条纪律是**构造上成立**的，没有第二个可以悄悄失配的副本。
- `ShowDirector` 的**塔层高**与**闸板下沿**改读 `coinColliderHeight(kind)`
  （写死普通币厚度会让宝箱塔**自相重叠** → 求解器把整座塔弹飞 → `anomalies`）。

#### 13.7.1 ★ 顺手修掉一条**概率性测试判据**

第一遍全量跑 **47 passed / 1 failed**：

```
tests/visual.spec.ts:211 › 重复开局是幂等的
  expect(mid?.chips).toBe(initialChips - 1)   Expected: 19   Received: 22
```

**这不是 S15 引起的**：投币之后那 30 帧里有一枚币越线结算了，`chips` **不降反升**。
那是**合法结算**，不是「扣多了」。佐证：同一条用例在 `desktop-chrome` 项目里同一次跑是绿的，
单跑 3 遍也全绿 ⇒ 纯概率性（与推板 1.8 枚/循环的节奏撞上就红）。

**修法**：把「一次投币只扣 1 枚」的读数从 `chips` 换成**消耗账本**，返值用三账本恒等式解释掉：

```ts
expect((mid?.spent ?? 0) - (before?.spent ?? 0)).toBe(1);
expect(mid?.chips).toBe(
  initialChips - 1 + ((mid?.earned ?? 0) - (before?.earned ?? 0)) + ((mid?.begged ?? 0) - (before?.begged ?? 0)),
);
```

改完 **两个项目 × 5 遍 = 10/10**，全量 **48 passed (6.4m)**。
教训与 `pace` / `economy` 同一条：**凡是「某一瞬间的余额」型判据都会被合法结算污染，
要读账本（累计量），不要读余额。**

### 14.5 ★ shader 通道：为什么只能是「全体统一注入」

已读 `node_modules/three/build/three.module.js` 求证：

| 事实 | 位置 |
| --- | --- |
| `material.onBeforeCompile(parameters, renderer)` 被调用 | `:18148` |
| 紧接着 `programCache.acquireProgram(parameters, programCacheKey)` | `:18150` |
| 命中全局 `programsMap` 时只 `++usedTimes` 返回**旧 program** | `:7988-8005` |
| **但 `materialProperties.uniforms = parameters.uniforms` 照常执行** | `:18153` |

⇒ 两条结论：
1. **注入的 GLSL 对程序缓存键完全不可见**（`ToonMaterial` 把 `customProgramCacheKey`
   盖成常量 `'toon-ramp-v1'`）⇒ **同 key 必须同 GLSL**，否则后者静默复用前者的源码。
2. **program 共享、uniforms 逐材质** ⇒ 「同一份 GLSL + 每材质不同 uniform」合法且安全。

于是唯一不撞顶格约束的路是：**对所有 toon 材质无条件注入同一段 GLSL，用每材质 uniform
控强度**。新增 define 一律不行 —— `perf` 的 `已编译程序数 ≤ 20` 现在**正好 20（顶格）**。

**注入三处**（顺序是 three 的固定顺序，不是我们排的）：

| 注入点 | 内容 |
| --- | --- |
| `<common>` 之后 | `RIM_DECL`：`uRimColor/uRimStrength/uRimPower/uRimEmissiveFloor` + `float sdRimFres` |
| `<normal_fragment_maps>` 之后 | `RIM_APPLY`：`sdRimFres = pow(1 - saturate(dot(normal, normalize(vViewPosition))), uRimPower)`，`diffuseColor.rgb += uRimColor * sdRimFres * uRimStrength` |
| `<emissivemap_fragment>` 之后 | `totalEmissiveRadiance *= mix(uRimEmissiveFloor, 1.0, sdRimFres)` |

`vViewPosition` 可用性已核实：`lights_toon_pars_fragment.glsl.js:2` 无条件声明、
`meshtoon.glsl.js:42` 顶点赋值；`normal` 由 `normal_fragment_begin` 声明为**视空间**。

★ **顺手收口了一个脆弱写法**：旧代码是两次独立的 `.replace('#include <common>', …)`
（detail 一次、rim 再一次）。两次插入会叠加，**嵌套顺序取决于调用顺序** ——
加第三个注入点时必然出事，所以合并成一次。

### 14.6 ★ 第一版 shader 的实测教训：**平铺自发光会抹平切面**

第一版只做了「边缘光加在 `diffuseColor` 上」，截出来**钻石是一团发光的白球**。
根因：`emissive` 是**与法线无关的平铺加色**，`kinds.ts` 里的 0.42 / 0.30 在模型
只有 124 mm 时无伤大雅，放大到 216 mm 之后就把逐面差异整个淹没。

修法两条一起上：
1. **自发光跟着菲涅尔走**（`emissiveFloor` 0.22 / 0.30）⇒ 边缘亮、正对镜头的面通透；
2. **模型币的自发光缩到 0.40 / 0.45 倍** —— ⚠️ 缩放写在 `coinTexture` 而**不动
   `kinds.ts` 的 `glow`**，因为那两个值同时被滚筒灯色（`xixi.ts`）消费。

第二版截图：宝箱读得出「亮色框架 + 深色面板 + 金色锁板」三档；钻石读得出八边形腰棱与切面。

### 14.9.1 ★ 一次完整的缺陷定位（「概率性红」该怎么查）

**现象**：`xixi` 连跑 5 遍，1 红 4 绿（≈ 20%），红的是 `anomalies=1`。

**第一步 · 让判据能说话。** 原来的判据只打一个数字（`anomalies=1`），
完全无法定位。改成把 `anomalySamples` 的明细打出来（帧号 / 币种 / 位置 / 速度）——
这是一条**永久改进**，不是临时调试。

**第二步 · 抓到样本**：

```text
#4641 bronze @(-0.615, -0.932, 0.278) v=(-0.42, -5.907, -1.179) |v|=6.039
```

一枚**铜币**掉到 y = −0.93（地板下），下落速度 −5.9 m/s。
按 `vy` 反推：它是在 `y ≈ 0.06`（**币床内部**）以约 −3 m/s 被挤下去的，
起点 `x ≈ −0.54, z ≈ 0.50` —— 那里**地板是实心的**（中路碰撞体覆盖 `|x| ≤ 0.66`、
`z ∈ [−2.35, 1.15]`）。所以不是「从洞里掉出去」，是**被挤穿地板**。

**第三步 · 排除法。** 单独跑「宝箱演出 + 钻石演出」的探针：**0 异常** ⇒ 不是演出本身。
再跑对照实验：把 S16 的尺寸（`MODEL_DIAMETER_RATIO`）与宝箱枚数回退到 S15，`xixi` 连跑 3 遍
**全绿** ⇒ **确认是 S16 引入的**。

**第四步 · 找到真因：钻石出生就嵌进台面币堆。**

`GateShow` 的出币高度原先写死 `TABLE.pusherTopY + 0.08 = 0.28`。拆开看那个 0.08 是
「台面静置币的顶（`2 × halfThickness = 0.024`）+ 余量 0.044 + **半个普通币**（0.012）」。

而 `GateShow` 也送钻石，钻石 S16 起高 **131.8 mm**（普通币的 5.5 倍）：
底沿落在 `0.28 − 0.0659 = 0.214`，而台面静置币的顶是 `pusherTopY + 0.024 = 0.224`
⇒ **出生就嵌进币堆 1 厘米**。求解器为了把它推出来会注入速度，
连锁反应表现为币床上的铜币被挤穿地板。

**修法**：把出币高度改成从**该币种自己的碰撞体**派生：

```text
spawnAtY = pusherTopY + 2 × halfThickness + GATE_RELEASE_CLEARANCE + coinColliderHeight(kind) / 2
```

`GATE_RELEASE_CLEARANCE = 0.044` 是**从原写死值反推的**（不是新拍的数）。
铜币算出来 0.2806，与原值 0.28 **实质相同**；钻石算出来 0.334，底沿 0.268 > 0.224 ✓。

**方法论**：这次是同一个坑的**第四种形态** —— 前三种是「层内偏移」「层高」「闸板下沿」，
全都是**写死「一枚普通币」的绝对尺寸，而调用方其实会送高得多的模型币**。
`ShowDirector` 里凡是出现 `COIN.halfThickness` / `COIN.radius` 的地方都要按这个模式再审一遍。

| 7 | `show` 模式 2 分钟以上，前台会被超时杀掉 | `Exit 137 / SIGTERM` | 长模式一律 `run_in_background` |

### 14.11 追加：删掉「中币抖屏」（用户原话「现在中币整个画面就会震荡，不要这个震动的动画」）

**删了什么**：`Game.triggerClimax` 里原先有一句
`this.shake = Math.max(this.shake, strength)`，由 `applyCameraShake` 换算成
`strength² × 0.055` 米的相机位移 —— 强度 1 的币种（大赏 / 钻石 / 宝箱）一越线，
**整个画面跳 5.5 厘米**，在 `sin(elapsed × 46)`（≈7.3 Hz）下衰减约 0.3 秒。

**保留了什么**：
- HUD 全屏闪色（`hud.flashClimax(tone)`）—— 用户没说要去掉，它是「中币」反馈的另一半；
- 三个 3D 自发光脉冲（得分线 / 热区 / 洞口）；
- **推板前推时的 2 毫米台面微震** —— 它只跟推板相位走，与「中币」无关，
  是「机器在动」的触觉提示。`applyCameraShake(delta)` 因此改名 `applyCameraRumble()`（不再需要 `delta`）。
- `feedback.climax.strength` 字段：它是分级结果的公开契约
  （`crossingFeedbackProbe` 的判据核它 —— 「连落白闪的强度是 1」），只是不再驱动相机。

**★ 为什么必须补一条判据**：抖屏是**只能靠逐帧观测发现的静默回归** ——
抖的是运动，**静止截图完全看不出来**。`shots` 模式与 `npx playwright test` 的截图断言
都抓不到它。所以在引擎里加了一个逐帧记账 `Game.cameraPeakOffset`（本局相机偏离
`cameraBase` 的峰值），由 `feedbackReport()` 交出去，判据断言
「本局峰值 ≤ 0.0025 米（微震上限 0.002 + 25% 余量）」。实测读数 **0.002 m**。

**顺手修掉的一条既有假红**：`feedback` 模式的「衰减回到基线」原先**固定等 700 毫秒**，
而 `playRun({ waitEnd: false })` 之后本局还在跑、推板继续把币推过线 ——
读到的可能是「刚跳了一下」而不是「衰减完了」（实测红：得分线 1.515 / 热区 2.142，
基线是 0.35 / 0.55）。改成**先停推板（`setPusherRunning(false)`）再轮询到回基线**（3 秒上限），
连跑 3 遍 11/11。

### 14.12 追加：微震也去掉 ⇒ **相机完全静止**

用户追加「微震也去掉」，于是第二路（推板前推时的 `sin(elapsed × 92) × 0.002`）也删除。

**现在的状态**：`fitCamera()` 把位置同时写进 `camera.position` 与 `cameraBase` 之后，
**没有任何代码改过相机位置**。`applyCameraRumble()` 只剩下一个空壳，改名
`trackCameraOffset()` —— 它只记账、不移动相机：

```text
trackCameraOffset()  →  cameraPeakOffset = max(已记峰值, |camera.position − cameraBase|)
```

**为什么空壳要留着**：它是这条删除的**唯一守卫**。相机运动在静止截图里完全看不出来
（`shots` 模式与 `npx playwright test` 的截图断言都抓不到），`camera.position`
也不在诊断快照里。判据改成断言**恒为 0**（`<= 1e-6`）。实测读数：
删抖动之前 **0.055** → 删抖动之后 **0.002** → 删微震之后 **0**。

**连带清理**：`setReducedMotion(true)` 里那句 `camera.position.copy(cameraBase)` 删掉
（没有微震可解冻了）；`MotionPrefs` 的注释改成「不再管任何镜头运动」。

### 14.13 已知残留：**求解器造能量**的低频概率性红（本轮未处理，刻意的）

`all` 模式（probe + endless + xixi）跑多次会偶发 1~2 条红，两条都是同一个根因的两副面孔：

| 判据 | 样本 | 含义 |
| --- | --- | --- |
| `probe` · 推板走一轮后没有超出物理上限的能量注入 | 压速 2 次，**峰值 13.233 米/秒**（自由落体上限 6.3） | 求解器在一轮推板里造出了 13 m/s |
| `xixi` · 全程无异常 | `#20122 bronze @(0.154, -0.867, 1.154) v=(-3.555, -4.795, 5.455)` | 一枚铜币被以 ≈8 m/s 弹出，越过得分线的同时落到地板下 ⇒ 异常判据（排在得分判据之前）先抓到它 |

**实测发生率**：

| 跑法 | 结果 |
| --- | --- |
| `probe` 单独 ×3 | **3/3 全绿**，峰值 **0 米/秒、压速 0 次** |
| `xixi` 单独 ×3 | **3/3 全绿** |
| `all` ×5 | **4 绿 1 红**（红的那次两条同时出现） |

**为什么判定它**不是**本轮改动引入的**：
`probe` 模式里**一枚模型币都不会出现**（预置盘面只有 bronze / pattern / payout，
`ENDLESS_SPEC` 里根本没有 diamond / chest），而它照样能红 ⇒ 与「模型放大」无关，
是**币堆刚度 / 求解器收敛**这条既有的敏感面。

**为什么本轮不修**：
唯一有效的旋钮是求解器迭代数（`COIN.additionalSolverIterations` / `PHYSICS.*`）。
而**币堆刚度是被标定过的量** —— 项目纪律写得很清楚：「改推板行程 / 台面长度 /
币床几何 / **币堆刚度**之后必须重标返值表」。动它就会牵出 `pace`（26 毫米/循环净前进）、
`physics`、`economy` 一整串重新标定。用户本轮明确「先不管数值，不做数值相关的检测」，
所以**刻意留给下一轮**，这一轮只把现象、样本与发生率记录下来。

**下一轮的最小验证方式**：`for i in 1 2 3 4 5; do node scripts/verify-game.mjs all; done`
—— 现状是 5 次里约 1 次红（实测 `all` ×5 = 4 绿 1 红），改完必须做到 5/5。
