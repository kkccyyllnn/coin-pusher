## 1. 设计目标与原则

**目标**：新手 10 秒看懂「现在该干什么」，单手能玩，机台从「工程面板」变成「街机」。

三条原则（继承 v1 的支柱，不许破坏）：

1. **物理唯一裁判**。所有动效只放大物理已发生的事，不伪造结果。推板收窄后推进变慢是物理决定的，不用动画假装变快。
2. **信息分层**。同一时间只让玩家做一个决策：选位（现在）→ 投币（现在）→ 加力（攒够时）→ 收割（收尾时）。UI 任何时刻只高亮当前那一个。
3. **可读性 > 装饰**。颜色是玩法信息：铜币=10、花纹=30、绿色=返币、金色=加力就绪，不许再加会撞色的外观。

## 2. 改动点一：钉阵显示长度缩短 1/3（只改显示，不改物理）

### 2.1 现状

`TableBuilder.ts` 的钉阵是 **22 根沿 z 轴伸出的横杆**（4 排：y = 0.62 / 0.80 / 0.98 / 1.16，每排 5~6 根，全部落在落币面 z = −0.72）：

| 项 | 值 | 说明 |
|---|---|---|
| `PEG_HALF_LENGTH` | 0.15 米（全长 0.30） | 碰撞体半长，物理用 |
| `PEG_RADIUS` | 0.008 米 | |
| 屏幕观感 | 在 1680px 宽的截图上，每根钉子投影长 **57~80 px**（越靠近镜头越长） | 正对镜头看是一根根长条 |

钉子太长时，整片钉阵在画面上是一排排长斜杠，把台面与币床的注意力抢走；正对镜头的那两根（x=0）更会被读成「背板中轴上的一根长柱」而不是一根钉子。

### 2.2 设计：缩短显示，碰撞体一律不动

| 项 | 现状 | v2 |
|---|---|---|
| 钉子网格长度 | 0.30 米 | **0.10 米（= 1/3）** |
| 钉子碰撞体长度 | 0.30 米 | **0.30 米（不变）** |
| 缩短方式 | — | **对钉子中心对称**，所以屏幕位置与币的命中点都不动 |

代码落点（`TableBuilder.ts`）：

```ts
const PEG_HALF_LENGTH = 0.15;                    // 碰撞体半长：物理，不动
const PEG_VISUAL_HALF_LENGTH = PEG_HALF_LENGTH / 3;   // 网格半长：纯显示
```

- 网格用 `PEG_VISUAL_HALF_LENGTH`，碰撞体仍用 `PEG_HALF_LENGTH`。
- **为什么不会「撞到一根看不见的钉子」**：可见段是 z ∈ [−0.77, −0.67]，而落币的 z 抖动范围恰好是 `TABLE.drop.jitterZ = 0.05`（即 ±0.05），两者完全重合——币永远落在看得见的那一段上。
- **常量下限**：`PEG_VISUAL_HALF_LENGTH` 不得小于 `TABLE.drop.jitterZ`（也就是比例不得小于 1/3），否则可见段盖不住落点。这条写进常量注释。

### 2.3 状态

**已落地**（`src/systems/TableBuilder.ts`，工作区未提交）。待补：把钉子长度暴露进诊断对象，让验收能断言「网格 0.10 米 / 碰撞体 0.30 米」——现在 `Game.probeColliders()` 只读 cuboid 的 `halfExtents()`，圆柱读不到半高，需要补一个分支。

## 3. 改动点二：推子行程收窄（留更多金币在盘面）

### 3.1 现状与问题

`constants.ts`：`pusherTravel = 1.0` 米，推币面从 z=-0.16 推到 z=0.84，得分线在 z=1.15。距离只剩 0.31 米。

v1 的实测已经暴露出这个问题：

| 行程 | 得分（20 投，机器人） | 每循环推下 | 体感 |
|---|---|---|---|
| 0.80 米 | 60 | 0.29 枚 | 推不动，憋死 |
| **1.00 米（现状）** | 220 | 1.22 枚 | 渐进，但峰值偏高 |
| 1.16 米以上 | 260+ | **8.67 枚** | **一波推光整堆** |

你提的「一下把所有金币全推出来」，正是 1.16 米以上的行为；1.00 米处于临界点，推币面已经伸到币床深处，币堆来不及恢复。

### 3.2 设计：行程收窄 + 盘面加密

两件事一起做，单靠行程解决不了：

| 项 | 现状 | v2 | 理由 |
|---|---|---|---|
| 推子行程 `pusherTravel` | 1.00 米 | **[待实测] 先扫描 0.55 / 0.62 / 0.70 / 0.78 / 0.85 再定值** | 行程是整机最敏感的数值，v1 就是实测定的；候选 0.70 米时推币面最远到 z=0.54，离得分线 0.61 米 |
| 盘面预置密度 | 主区 4 行 × 6~10 列 | **主区 5 行 + 加密列数、币量 +40%** | 见 §3.5：6 行在几何上不可行，只能靠加列 |
| 每循环推下目标 | 1.22 枚 | **0.6~0.8 枚** | 推进变慢、币床可视地持续有币 |

**关键点**：行程收窄后，推币面够不着的币只能靠币堆整体传递。这正是你要的「推一点、进一点」，而不是「推一次、推一片」。

### 3.3 必须重测的事（不许拍脑袋定目标分）

行程是整机最敏感的数值，v1 就是靠实测扫描定下来的。收窄后**必须重扫**：

1. 用 `scripts/verify-game.mjs sweep` 在 `SWEEP=0.55,0.62,0.70,0.78,0.85` 上各跑一遍，取每循环推下枚数。
2. 选「每循环 0.6~0.8 枚且盘面不憋死」的最小行程作为基准（预期落在 0.62~0.78 之间）。
3. 按新行程重新测每关可达分数，下调目标分（预计第 1 关 140 → ~90~110，依实测）。

**失败信号**（写进验收）：

- A：选定的行程下，前沿币堆**连续 8 个循环**看不到新币越线 → 行程太短，币堆断了。
- B：第 1 关机器人 20 投拿不满 80 分 → 行程与盘面密度不匹配，往加币的方向调。
- C：出现「一波推光」（单循环 ≥ 5 枚越线）→ 行程又调大了。

### 3.4 与平衡性设计方案的关系

那份方案里指出「第 2 关是全游戏最难通关的关卡」（需榨出上限的 72.6%）。行程收窄会让所有关推进变慢、变难——**这两条必须一起看**：

- 本计划只处理「推子与盘面」，第 2 关难度塌腰按设计方案第 7 节的「修曲线」单独处理（降目标或加花纹）。
- 不要在同一个版本里既收窄行程又抬目标分——一次只动一个变量。

### 3.5 硬约束：盘面加密的几何上限（源码核算，别按「5~6 行」拍）

`levels.ts` 的 `assertLayoutValid()` 要求**同一层任意两枚币的间距 ≥ 币径 × 0.98 = 0.1176 米**，否则直接抛错。主区 `FIELD` 的 z 跨度是 0.54 米（z ∈ [0.36, 0.90]）：

| 主区行数 | 行距 | 结论 |
|---|---|---|
| 4 行（现状） | 0.180 | ✅ |
| 5 行 | 0.135 | ✅ |
| **6 行** | **0.108** | ❌ **小于 0.1176，会直接抛错** |

所以密度方案只能是 **5 行 + 加密列数**。若一定要 6 行，必须同时把 FIELD 的 z 跨度扩到 ≥0.60（例如 zMin 退到 0.30），并检查与前沿行 `FRONT`（z = 1.06，单行 8 列）不重叠——`FRONT` 与主区同一层，间距不够同样会抛错。

## 4. 改动点三：投币交互改为匀速自动选位

### 4.1 现状

`InputController.ts`：玩家靠拖动指针（`aim(clientX)`）或 A/D 键把选位移到目标落点，再按空格/点按钮投币。单手玩必须按住拖动，手机上尤其别扭。

### 4.2 设计：匀速自动选位（默认）+ 手动接管（兜底）

**默认**：选位标记自己匀速左右往返，玩家只负责在对的瞬间投币——单手、单手就能玩。

| 项 | 设计 |
|---|---|
| 运动轨迹 | **三角波**：到左缘反弹向右，到右缘反弹向左 |
| 往返范围 | x ∈ [−0.68, +0.68]（与现有一致） |
| 速度 | **匀速 0.62 米/秒**，一趟完整往返约 4.4 秒 |
| 起步位置 | 居中（x=0），开局向右走 |
| 暂停时机 | 玩家按住 A/D 或拖动 → 进入 2 秒手动接管，松手后 2 秒恢复自动 |
| 投币 | 空格 / 投币按钮 / 触屏**任意处轻点**（只触发，不选位） |

**手动接管规则**（避免「我想自己控制却被自动打断」）：

- 玩家一碰 A/D 或指针，自动选位立即停 2 秒；持续操作时一直手动。
- 松手 2 秒后，自动选位从当前位置继续，不跳变、不回中。
- 在 HUD 上给一个一眼能看懂的状态：自动选位时标记呼吸摆动，手动时标记高亮静止。

**为什么用三角波不用正弦**：匀速是硬要求（你指定的「匀速左右」）。正弦在两端减速，会让选位在两侧停留更久，等于暗中加权了两侧落点——三角波每个落点停留时间完全一样，公平。

**失败信号**（写进验收）：

- A：自动往返速度在两端不为零/不平滑（测速曲线应是一条平线折返）。
- B：手动接管后松手，选位跳回中心而不是从当前位置继续。
- C：自动选位导致玩家「永远等不到」目标落点——单趟往返 > 6 秒就要把速度提到 0.8 米/秒。

## 5. 改动点四：全新界面布局

### 5.1 布局原则：新手 10 秒看懂

把「现在该干什么」做成唯一高亮项，其余压暗。按视线顺序排：

```
┌─────────────────────────────────────────┐
│ 关卡名（左）        目标进度条（中）  暂停│  ← 顶栏，一行
├─────────────────────────────────────────┤
│  三路集章（左·中·右 小圆点，融入台面下缘）  │
├─────────────────────────────────────────┤
│              （机台画面）                  │
│   落点标记 ＋ 自动摆动的选位滑块（顶部）    │
├─────────────────────────────────────────┤
│  剩余投币（大号数字）        [加力] [投币] │  ← 底栏
└─────────────────────────────────────────┘
```

对比现状的三处结构改动：

1. **分数改成进度条**。现在是「0 / 140」纯文字，改成一条从左到右填充的进度条，达标线处有一个刻度——玩家一眼知道还差多少，不用心算。
2. **集章融入台面**。现在是悬浮在屏幕中间的胶囊条，改成贴在币床上缘的一排小圆点，和台面一体，不再挡画面。
3. **底栏操作区分左右**。左：剩余投币（大号）；右：加力（充能态）+ 投币（主按钮，最大）。加力未充能时不显示，而不是置灰——没充能时这个按钮根本不该出现。

### 5.2 组件清单（每个组件的默认/悬停/按下/禁用态都要画）

| 组件 | 状态变化 |
|---|---|
| 目标进度条 | 普通填充 / 接近达标时末端发光 / 达标瞬间整条条脉动一次 |
| 剩余投币 | 数字 / 投出一枚时数字跳动 + 上方浮现一枚小铜币飞入机台的动画 |
| 投币按钮 | 默认呼吸 / 冷却中进度环转一圈 / 额度用尽置灰消失 |
| 加力按钮 | 未充能隐藏 / 充能就绪呼吸发光 / 按下后推板前缘闪一次 |
| 三路集章 | 灭 / 点亮（弹跳放大一次）/ 集齐时三点同时闪并滑向加力按钮 |
| 结算卡片 | 底部滑入 / 星级逐个点亮（不是一次全亮）/ 图鉴券单独弹一下 |

## 8. 验收标准与失败信号

用 `verify-game.mjs` 扩展新验收项，不许凭肉眼说「好看」：

| 验收项 | 通过标准 |

**热区为什么只在无尽模式开启**：战役六关的目标分是在**没有热区**的前提下实测出来的，直接开启会让六个目标分全部失真、必须重测一轮。设计文档本身也说热区是「可选轻量玩法，先不做，等 A/B/C 落地后看时机决策是否还需要加深度」——现在机关 A~D 已经给了时机与空间两个维度的决策，所以热区作为**无尽模式的方差放大器**落地（那里没有目标分，不需要重配平衡），战役侧留一个 `LevelConfig.hotZone` 开关，要开就得先重测那一关的目标分。

顺序约束：**先改界面与交互（①~④），再动平衡（⑤~⑦），最后接奖励闭环与新增玩法（⑧~⑯）**。交互稳定后再收窄行程、重测目标分——否则你会拿一个还在变的输入手感去配难度，两边都不准。⑧⑨ 必须一起落地：3 星不可达时不补券，券的来源永远补不上。

### 11.2 机关的实现约束（源码核算）

- **`PhysicsWorld` 没有「按区域查询币」也没有「移动币」的现成 API**（只有 `world` / `step` / `freeze` / 计数）。但 `CoinPool.coins` 是 public 数组、`Coin.body` 是 public `RigidBody`、`Coin.position` 可读，所以扫板与抓斗可以基于「遍历 + `applyImpulse` / `setLinvel` / `setTranslation`」新写（参考 `Coin.applyConveyor` 与 `Coin.spawn` 的用法）。若要「真实的挡板几何」，需照 `Pusher` 的模式新增运动学刚体并纳入每帧更新。
- **后装填可以直接复用投币链路**，不需要新物理能力。
- **`COIN.budget = 120` 是硬上限**：池满时 `acquire()` 返回 `null`，而 `Game.tryDrop` 现在是**静默失败**（不扣额度、不提示）。⑫ 后装填与 ⑮ 无尽模式的高频返币都会撞这个上限——**必须先定预算策略**（优先回收已静止的铜币 / 上调 budget / 满了就明确拒绝并提示），否则表现为「按了没反应」。

### 11.3 无尽模式（第 6 节）的落点与红线

| 子项 | 落点与要点 |
|---|---|
| 模式骨架 | `RunState` 现在的一切都由 `LevelConfig` 驱动（`credits` / `payoutReturnCap` / `channelMarks`），且 `addScore` 达标即 `enterSettle('success')`、`consumeCredit` 归零即 `'exhausted'`。无尽要**加一个模式开关或子类**，不要改 `LevelConfig` 的语义 |
| 金色大赏币 `bounty` | 新增币种要动 **5 处**：`constants.ts` 的 `COIN_KIND`、`cosmetics.ts` 的 `CoinPalette` 与 `KIND_LOCKED`、`coinTexture.ts` 的面值标记与自发光、`CoinPool` 的材质表与**换肤里硬编码的 `['bronze','pattern','payout']` 数组**、`Game.settleCoin` 的返币分支。⚠️ `COIN_KIND[*].creditBack` 字段**全项目无人读取**（现有返币走 `RunState.grantPayoutReturn()` 固定 +1），所以 +8 筹码必须新写分支，不能只填字段 |
| 热度倍率 | 最干净的落点在 `RunState.addScore`：把 `score += value` 移到 combo 计算之后，按 combo 取倍率并回传 `gained`。返币走独立的 `grantPayoutReturn`，天然不受倍率影响——正好满足「只放大分数、不放大筹码」 |
| 破产与「最后一枚绿币」 | 复用现有 `drainOut` / settle；沉降期间绿币或大赏币越线 → 自动复活 + toast（复用 `payoutReturn` 音效） |
| 嘲讽弹窗与跪求 | 可 1:1 套 `#result-panel` 的结构（`h2` 标题 + `dl` 统计 + `#result-actions` 两按钮），新增 `showBankrupt(payload)`；跪求递减 30→24→19→15→12→10；跪求保留盘面、收工清空盘面 |
| 本地排行榜 | `SaveStore` 加 `endlessBest` / `endlessBegs`（终身累计）/ 记录数组，沿用现有「逐字段防御式解析」的写法；三列：分数 / 0 次跪求 / 累计跪求 |
| 加注（1 / 2 / 5） | 最后做，等 ⑭⑮ 的数据再决定 |

**红线**：无尽模式**不发图鉴券**（否则是绕过效率星的刷券农场）；跪求**只给筹码**，不给分数、不给券。

**文案纪律**：嘲讽只嘲手气与决策，不嘲玩家本人；Tier 3 封顶，不升级到真正的恶意。

### 11.4 新增按钮的改动面（每个按钮 5 处）

`InputController` 现有 5 个按钮（`#drop-button` / `#boost-button` / `#retry-button` / `#next-button` / `#giveup-button`），每个按钮要动 5 处：① `LaneInput` 加字段；② 加 `onXxxClick` 与 `xxxQueued`；③ 构造函数加注入参数与 `addEventListener`；④ `sample()` 组装与清零；⑤ `dispose()` 移除监听；另外 `Game.ts` 传入元素。**弹窗按钮（破产弹窗的跪求 / 收工）建议直接在 `Hud` 里绑定**（照 `bindPauseToggle` 的做法），避免污染输入帧采样。

（注：`#pause-button` 与 `#collection-button` 不走 `InputController`，分别绑在 `Hud.bindPauseToggle` 与 `CollectionPanel` 内。）
