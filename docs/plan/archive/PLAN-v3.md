## 4. P1 执行中发现的问题

### 4.1 期望值必须用真物理实测标定，闭式解会漏项

原定的 `bronzePayoutChance = 0.55` 让期望变成正的，**局永远不会结束**。
实测：89 投赚进 155、消耗 89（回收率 1.74）。根因是规划只算了
「铜币 E = 0.55 × 1.5 = 0.82 < 1 就安全」，漏了两项：

- 花纹筹码基数 3 且**不过闸门**，占越线枚数 10% 却贡献 0.43/投；
- 实测越线/投币 = 1.20（多出来的 0.2 是开局预置的 74 枚被推下去，每局都会重置）。

三次标定：`0.55 → 1.74`（永不结束）、`0.37 → 0.91`（200+ 投的长局）、`0.28 → 0.68~0.75`（采用，
区间见 §3）。**注意 `0.28` 是在旧收尾行为下标定的**，见 §4.5 的注。

**P2 换满盘排布后越线/投币比会变，P8 必须用 `economy` 模式重新标定并回写 `constants.ts`。**

### 4.2 「200 局净流出 > 0」这条验收本身是恒真的，不能当判据

「一局在筹码归零时结束」这条规则直接蕴含 `赚进 − 消耗 < 0`，所以它测不出任何东西。
真正有判别力的是**单位期望**（每投入 1 枚筹码的期望回收）与**局的长度**。
`economy` 模式两条都断言了。

### 4.3 `playRun` 的「投固定 N 枚」写法在负期望下失效

回收率 0.79 时投 26 枚手里还剩一半，局不结束，`waitForRunEnd` 一直等到超时。
已改成「投到本局终态为止」，`drops` 只作防死循环上限。

### 4.4 币面不能再印面值

旧贴图印的是 10/30/+1（v2 的分数体系），在新口径下全是假数字。
改成身份符号：铜币留白、花纹「花」、返币「＋」、大赏「赏」。
同时删掉 `COIN_KIND` 里没人读的 `score`/`creditBack`，新增 `COIN_BASE_CHIPS`
作为「币面印什么」与「返多少」的单一真源。

### 4.5 ★ 把 score 与 credits 合并成 chips 时，顺手让「每一笔返值都能取消沉降」——这条把收尾机制打死了

v2 的分工是：铜币/花纹越线给 **score**（不复活），只有绿币/大赏币给 **credits**（复活），
所以收尾必然能走完。v3 统一成一个账本后 `gainChips` 一律调 `revive()`，
于是**沉降期的第一次返值就把沉降取消掉**。

实测（`setState('drain')` 满盘进收尾）：约 **1.2 秒**就有一波 12 枚币越线、返 12 筹码，
沉降当场结束，`plateStopped` 永远到不了。后果是连锁的：

- `mechanisms` 的「收尾能走到停板」失败，扫板（开放条件是「收尾 + 停板」）跟着失败；
- `accept` ⑩ 三条全灭：收尾记录被清空 → 原因「未知」、持续 0.0 秒、看不到迟到返值；
- **⑩「进入收尾后仍能获得迟到返值」在旧实现下是恒假的**——返值一来就取消沉降，
  所以「走完的收尾」必然是「零返值」的那一种。
  **断言恒假 = 实现跑偏了，不是断言写错了。**

修法：

- `RunState.gainChips` 不再动沉降状态；`grantBeg`（跪求）保留 revive，是唯一救济；
- `Game.updateRunState` 在沉降走完那一刻判定：手里**有筹码 → 本局继续**（`reviveFromRuin`），
  **一枚都没回吐 → 破产弹窗**。不能在这里悄悄结束本局，那等于把返值吞掉；
- `Telemetry.recordDrainStart` 改成**每次覆盖**、删掉 `clearDrain`，
  `resetDrainRecord` 只复位 Game 侧的一次性标志——原来的「清记录」逻辑会把
  刚走完的收尾记录擦掉，断言就再也读不到了。

**顺带发现（P7 必读）**：停板窗口只有不到 1 秒（停板后盘面静止 `RULES.restHold = 0.8` 秒
收尾就走完），扫板/转轮在真人手里基本按不到。**P7 重做四机关时必须把这个窗口做宽。**

### 5.1 P1 收尾时修掉的真实缺陷

- **开局买入被扣了两次钱包。** `Game` 构造函数里 `this.run = new RunState(config, save.buyIn())`
  先扣一次，紧接着构造函数末尾的 `startRun()` 又扣一次——每次打开页面钱包少 40，
  而局内只有 20，多出来的 20 谁也拿不到。其他验证模式因为都先调 `clearSave()`
  （把钱包重置回 200）而**把这个问题完全掩盖了**，只有存档迁移用例暴露出来。
  修法：构造函数里那个实例改成不碰钱包的占位（`new RunState(this.config)`），
  买入只发生在 `startRun()` 一处。

### 5.2 待用户决定（不是 bug，是设计取舍）

**「打开页面即开一局」会立刻从钱包扣掉买入（20 筹码），所以刷新页面等于白扣 20。**

- 现状：`Game` 构造函数末尾调 `startRun()`，开局满盘（这是无尽模式「一进来就是满盘」的观感来源），
  而买入是开局的一部分，所以一加载就扣。
- 影响：误刷新 / 误关页面会丢 20 筹码（起始钱包 200 的 10%）。反复刷新能把钱包刷空，
  而钱包空后只能靠「跪求 → 打回来 → 收工回存」恢复。
- 三个可选方案：
  1. **保持现状**（「上桌就押注」，赌局语义最一致）；
  2. **把扣款推迟到第一枚币投出时**（`startRun` 只记 `pendingBuyIn` 不扣钱包，
     首投再调 `save.buyIn()`）——刷新不再损失，但 HUD 在「准备」阶段会显示
     「钱包 200 / 局内筹码 20」，两者相加不等于起始值，需要文案上说得通；
  3. **把在桌筹码持久化**（存档里记 `committed`，刷新后复用而不是重新买入）——
     最接近「玩家不亏」，但要新增一个存档字段与一条状态路径。

  默认先按 1 走（不改），等确认。

### 6.2 ★ 满盘化把推板行程从 0.84 打回 0.30（P2 最关键的一处发现）

满盘之后 0.84 米的行程**把整张币床当刚体推走**。`pace` 实测：

```
盘面 310 枚，0.84 米行程 → 23 个循环推下 193 枚，平均 8.391 枚/循环，
                          单循环最多 106 枚（一次垮塌带下盘面的 1/3）
```

推进速度超标 2.8 倍，而且那 106 枚的「一波推光」正是 `pace` 模式要拦的东西。

根因是**几何死区**：旧盘面的币床从 z=0.32 才开始，而推板归位前缘在 -0.16，
中间 0.48 米是空的 —— 行程必须拉到 0.48 米以上才碰得到币，而一旦行程长过
「推板到币床后沿 + 币床深度」，整床币就会被一次性扫出去。

参考项目（coin-pusher-2000）的币床是**从推板前缘一直铺到前沿、没有死区**的，
它的行程只有 `sin(phase) × 0.10`（峰峰 0.2 米）。按这个比例重排后重扫：

```
0.20 米 → 0.217 枚/循环，最长空档 17 个循环（憋死）
0.30 米 → 0.522 枚/循环，最长空档 6，单循环最多 2 枚
0.36 米 → 1.087 枚/循环，最长空档 4，单循环最多 12 枚   ← 选定
0.45 米 → 1.826 枚/循环，最长空档 5，单循环最多 24 枚（接近「一波推光」）
```

**为什么最后是 0.36 而不是看起来更「稳」的 0.30**：0.30 的推进率只有 0.52 枚/循环，
于是「越线/投币」掉到 0.70、回收率掉到 0.444——单局只剩 40 投左右，既低于
「一条命 60~90 投」的设计目标，也让 `economy` 模式的长度断言失守。
**推进率是经济的输入**（`crossings / drops`），选行程不能只看「憋不憋死」。
换到 0.36 之后：越线/投币 1.156、×1 档回收 0.743、单局 67~68 投，全部回到设计带内。

0.36 给出 1.087 枚/循环，与旧盘面的 1.22 枚/循环接近，所以 `bronzePayoutChance`
的标定大致仍然成立 —— 但**必须由 P8 用 `economy` 模式重新核对，不能假设**。

### 6.3 排布引擎的三条关键设计（踩过才知道）

1. **`pick` 是前缀语义**：取「按种子洗过的序列」的前 N 个，所以「抽 30 个」必然是
   「抽 48 个」的**子集**。上层币因此一定压在下层币上，不会出现开局就往下掉的悬空币
   ——「静置 10 秒全静止」这条验收靠的就是它。
   （第一版用「均匀抽样」，两层各自抽，上层币悬空，静置直接失败。）
2. **同几何的网格按签名缓存顺序与抖动**：花纹与返币要撒在同一层的不同格子上，
   靠「同一份洗过的序列、各取一段」错开。第一版每个区域各自洗牌，
   两次洗出来的顺序不同、`pickFrom` 完全错位，两批币撞在同一格上
   （自检报「盘面重叠：(0.722, 0.924) 与 (0.724, 0.924) 间距 0.002」）。
   缓存顺带保证同一格子在所有层拿到同一份抖动，叠起来的一摞是正对的。
3. **`surface` 必须显式标记台面**（bed / deck），不能靠 `y > pusherTopY` 猜：
   币塔上层会高过推板顶面，用 y 判会把塔顶的币误判成上层币，于是自检放过一批真正该报错的坐标。

### 6.4 自检新增的三条（其中一条卡死了币塔高度）

- 上层币必须在推板后缘与归位前缘之间；
- 上层币必须落在**台面输送带**（`TABLE.conveyor` y ∈ [0.14, 0.34]）里，否则它不会被输送向前、上层就死住了；
- **币床币不得落进台面输送带**。这一段是给推板顶面用的，币床的币一旦落进去就会被持续施加
  向前的冲量、堆好的盘面自己散架。**这条同时卡死了币塔的高度上限**：
  层高 `LAYER_STEP` = 0.0212，所以塔最多 6 层（塔顶 y = 0.118 < 0.14）。
  想要更高的塔，得先把 `conveyor.minY` 抬到推板顶面之上。

### 6.5 台面输送必须设闸门（否则上层一秒内空掉）

输送带 0.85 m/s、上层币离前缘只有 0.12 米 —— 预置的上层币如果也吃输送，
**不到一秒就被整片冲下前缘**（这正是规划里预警的那条）。
修法：输送**只作用于 `playerDropped` 的币**。预置的上层币只吃推板顶面的摩擦，
于是随推板前后滑动、停在原地 ——「推币台上下都有金币」的观感留住了，
实测上层留存 18 → 18。

### 6.8 ★ 还有一条：检查自己把钱包花光了

`accept` 的 ⑨（返币）反复报「返币从来没发生过」，我先后怀疑布局、怀疑币种配比、
怀疑最前沿的币根本不动——**全错**。真正的原因是：accept 前面的检查每个都要 `startRun`，
而开局会从钱包扣 20；跑到 ⑨ 时钱包已经见底，`buyIn` 变 0 → **一枚币都投不出去** →
0 次越线 → 自然 0 次返币。证据就在 ⑩ 那一行：「筹码 31 = **买入 0** + 赚进 31」。

教训：**一条排在长套件靠后的检查，不能假设它依赖的共享资源还在**（这里是钱包）。
症状会伪装成「游戏机制坏了」，而实际是「这条检查自己没币可投」。
修法是检查开头显式复位（`clearSave()`），并且把这条理由写进注释——
否则下一个人还会去怀疑游戏。

## 6.10 ★★ 真正的开口不是「1 对穿模」，而是**整堆币沉进地板**（`PHYSICS.erp` 太小）

§6.9 把 ④ 的失败记成「1 对同层重叠、间距 0.0742 米」。往下一查，那只是**症状**，
真因是**整个盘面被压穿**。这一节是完整链条，因为它改变了三条验收判据的写法。

### 1. 起因：断言取的是「某一瞬间的快照」

同一条盘面反复跑 ④，报数在「0 对 / 1 对 / 3 对」之间摆动。**摆动说明这是在赌运气**
（§6.7 的老教训），所以先把场景改成确定性的：

> 跑到第 10 个循环 → **停推板**（新增钩子 `setPusherRunning(false)`）→ 等币堆速度 < 0.08 m/s → 再量。

这样量到的才是「稳定下来的穿模」，同一条盘面每次跑结论一致。

### 2. 顺着确定性场景量下去，看到的不是 1 对，而是整盘塌陷

新增诊断字段（`coins()` 里加 `tiltDeg` / `sleeping`，以及 `castDown` / `probeMeshes`
两个钩子）之后，同一个「静置」状态下的真实数据是：

| 量 | 实测 | 应该 |
| --- | --- | --- |
| 币心在地板顶面（y=0）以下的枚数 | **300 / 318** | 0 |
| 最低币心 | **−0.025 米** | 0.010 |
| 同格层间距（上下两层币心距） | **0.0084 米** | 0.0212 |
| 处于 `sleeping` 的币 | **278 ~ 298 / 318** | 视情况 |
| 从币心向下的射线第一个命中 | **地板碰撞体本身，toi = 0**（起点已在体内） | 地板顶面 |

也就是说：**币堆被压进地板 24~35 毫米，层间距被压掉 60%，然后一起睡着了**
（睡眠会冻结穿透修正，所以它就这么定住了）。方向性证据：`shots/endless-ready.png`
（该缺陷引入之前拍的）里币堆是有厚度的、币塔清晰；现在的画面里币堆是「一层薄饼」——
俯视看只看到币的**顶面**，所以肉眼看「好像没问题」，这正是它一直没被发现的原因。

### 3. 单变量试出来的根因：Rapier 的默认接触刚度太软

判据用「静置 2.5 秒后：沉入地板的枚数 / 最低币心 / 同格层间距」：

```
重力 −13（不变）
  erp 0.20（Rapier 默认）→ 299 枚沉入 / −0.0250 / 0.0084   ← 盘面被压穿
  erp 0.35               → 142 枚沉入 / −0.0060 / 0.0131
  erp 0.50               →  95 枚沉入 /  0.0030 / 0.0167
  erp 0.60               →  53 枚沉入 /  0.0060 / 0.0177
  erp 0.70               →   0 枚沉入 /  0.0080 / 0.0182
  erp 0.80               →   0 枚沉入 /  0.0080 / 0.0183   ← 采用
```

同一批实验里另外两件事**单独调都没用**，这条很重要：

- `solverIterations` 4 → 16：沉入 299 → 293（几乎没动）；
- 重力 −13 → −8（载荷降 38%）：沉入 299 → 247（仍然整盘沉）。

**所以瓶颈是刚度，不是迭代次数、也不是载荷**。先加迭代是白烧算力；刚度上来之后
再加迭代才有收益：

```
erp 0.80 + 迭代  4 → 币↔币最深  8.0mm、币↔机台  3.0mm，超 4mm 的接触 26 处
erp 0.80 + 迭代  8 → 币↔币最深  2.0mm、币↔机台  2.0mm，超 4mm 的接触  0 处  ← 采用
erp 1.00 + 迭代  4 → 币↔币最深  5.0mm、币↔机台  2.0mm，超 4mm 的接触  4 处
erp 0.80 + 币额外迭代 2 → 币↔币最深 4.0mm
```

（对照：`erp 0.20` 时币↔机台最深 **39.0mm**、超 4mm 的接触 **3360 处**。）

2.0 毫米正好是 Rapier `allowedLinearError`（默认 1 毫米）的量级，即「求解器已经修到
它认为不必再修」——所以到此为止，再往上调只烧算力。

**已落地**：`PHYSICS.erp = 0.8`、`PHYSICS.solverIterations = 8`（两个常量都写了完整推导）。
另外把「币额外迭代」`COIN.additionalSolverIterations` 从 1 回退到 0：A/B 实测它与本缺陷无关，
不是它引入的（但也不是它修好的）。

### 4. 判据跟着改：从「几何启发式」换成「引擎的接触穿透」

旧的 ④ 是几何启发式（同层 Δy < 0.01 **且** 横向距离 < 币径 × 0.9 → 算一对穿模）。
币堆变硬之后它开始**误报**：实测有「平躺币 + 46° 斜币、币心相距 79 毫米」这种
完全合法的倚靠（斜币的边缘搭在平币面上），被它一律判成穿模。根因是启发式只看
「币心距离」，而两枚斜币可以合法地靠得很近。

**改成读接触流形的 `contactDist`**（负值即穿透），也就是让引擎自己报穿透量——
与姿态无关，且这正是「穿模」的定义。新增钩子 `penetrationReport(limitMm)` 返回：

- `coinDeepest` / `staticDeepest`：币↔币、币↔机台的最深穿透；
- `overLimit`：超过阈值的接触处数；
- `worst`：最深几处的深度、涉及对象与坐标（诊断用）。

新的 `physics` 模式判据（8 项）：

```
① 静置 10 秒：不结算、不丢币、无异常、推板不动
① 静置 10 秒：全部币静止
② 推板 10 循环跟得上实时（墙钟 ≤ 理论 × 1.05）
② 推板不把盘面一次推光（枚数 ≥ 预置 75%）
③ 上层留存 ≥ 85%
④ 币堆静止后没有互相穿插（引擎穿透判据）—— 币↔币 ≤ 10 毫米、币↔机台 ≤ 4 毫米
⑤ 币床的币坐在台面上（没有整堆沉进地板）—— 币心不得低于「地板顶面 + 币半厚 − 2 毫米」
```

**⑤ 是这次新加的，也是唯一能照出本缺陷的一条**：缺陷状态下 ①②③④ 全部通过——
币确实「静止」（一起沉下去、然后睡着），也确实「没互相穿插」（点阵是一起平移的）。

### 5. 币堆变硬之后必须重量的两项

推进率是经济的输入，刚度会改变推板每行程推下的枚数：

| 指标 | 软币堆（erp 0.2） | 币堆修正后（erp 0.8 / 迭代 8） |
| --- | --- | --- |
| `pace` 推进率（行程 0.36） | 1.087 枚/循环 | **1.043 枚/循环**（仍在 0.3~3 带内，最长空档 5，单循环最多 11） |
| 单局长度 / 回收率 | 67 ~ 68 投 / 0.711 | **见 §6.11** |

## 6.12 ★ 经济的新开口：回收率在**单局内**随盘面排水爬升（正反馈）

§6.10 把 `PHYSICS.erp` 从 0.2 提到 0.8 之后，币堆变硬、推力传得更直接，
**越线/投币比从 1.156 涨到 1.440**，于是 `bronzePayoutChance` 必须重标（0.28 → **0.18**）。
重标后第 1 局的读数回到设计带内：**49 投 / 回收 0.59**，与 `20 ÷ (1 − 0.59) = 49` 完全吻合。

但复测暴露出一个**比标定值更根本的问题**：同一组常量下，局长是**双峰**的。

### 实测（`bronzePayoutChance = 0.18`，同一台机、同一套常量）

| 局 | 起点盘面 | 起始筹码 | 投币 | 回收率 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 第 1 局 | 满盘 318 | 20（买入） | 49 | **0.59** | 破产，落在设计带内 |
| 第 2 局（跪求后） | **保留的第 1 局残盘** | 30（跪求） | **≥160** | **≥0.82** | 到 160 上限仍未破产 |
| 历史对照（软币堆 `erp 0.2` / p 0.28） | 满盘 | 20 | **238** | 0.968 | 撞脚本超时 |

第 2 局的期望局长 `30 ÷ (1 − 0.82) ≈ 167` 投——**160 的上限刚好卡在它下面**。
也就是说它报出来的不是「机制坏了」，而是「经济在长局里透支」。

### 机制：`perDrop` 是**盘面占用度的函数**，不是常数

实测越线/投币比随局长上升：`L = 39 → 1.179`、`L = 98 → 1.337`、`L = 238 → 1.483`。
物理上说得通：盘面越满，推板一个行程主要在做**压实**（推力被币床吸收掉）；
盘面被排水之后，剩下的币都挤在得分线附近，**同一个行程能直接扫下好几枚**。

于是形成正反馈：

```
局越长 → 盘面越空 → 越线/投币比越高 → 回收率越高 → 局更长 → …
```

它在「回收率 ≥ 1」处成为**不发散的自持状态**，局永远不会结束——也就是「庄家终赢」失守。

### 为什么「调小闸门」治不了它（P2 期间扫了三次，都是白扫）

把 `perCrossing` 按老标定（p = 0.28）拆开：
**铜币项 0.361 / 次越线**（线性于闸门）、**闸门无关项 0.312 / 次越线**（花纹不过闸门 + 返币 3 + 大赏币 8），
合计 0.673。铜币项对闸门的斜率 = `0.361 ÷ 0.28 = 1.289`，所以

```
回收率 ≈ perDrop × (0.312 + 1.289 × bronzePayoutChance)
```

代进去就能看出**没有一个闸门值能同时满足两端**：

| 闸门 `c` | 满盘（`perDrop` 1.18） | 排水后（`perDrop` 1.67） | 结果 |
| --- | --- | --- | --- |
| 0.18（现用） | 0.642 → 约 56 投 | **0.909** → 局不结束 | 第二局超长 |
| 0.22（满盘刚好 0.70） | 0.700 → 约 67 投 | **0.99** | 更糟 |
| 0.083（排水后也 ≤ 0.70） | **0.494** → 约 40 投 | 0.700 | 第一局太短，低于设计目标 60~90 |
| 0（闸门全关） | 0.368 | **0.521** | 仍有 0.52 底，且全靠固定值币 |

`perDrop` 到 1.67 时，闸门关到 **0** 也还剩 `1.67 × 0.312 = 0.52` 的回收率。
**所以「一个有判别力的闸门值」并不存在**——这是这台机当前经济模型的结构问题。

### 结论（P8 的输入）

1. **`bronzePayoutChance` 不是这个开口的解**，不要再靠扫它找落点。它现在取 0.18，
   满盘端略偏紧（约 56 投 vs 设计 60~90），但如果为了满盘端把它抬到 0.20~0.22，
   排水端就会直接冲到 0.92~0.99。**先不要动它**，等正反馈被打断之后再一起定。
2. 真正的解是**打断正反馈**，两个方向（都要独立标定、都要一次只改一项）：
   - **闸门跟着盘面占用度收**：`crossingReturn` 加一个 `occupancy` 入参，
     满盘开闸、盘面见空收闸。**这是纯函数加一个入参**，可测、可回滚，
     主题上也对——「庄家只在库存厚的时候给钱」。
   - **压低闸门无关的那三项**（`payoutChips` 3 / `bountyChips` 8 / `bountyEveryDrops` 30 / 花纹配比），
     把 `0.312 / 次越线` 这个**底**降下去。纯数值，代价是「稀有兑现」的手感变差。
3. **P8 的标定工具要改**：`ECON_RUNS=200` 的**真物理**局不可行——
   每局按推板节奏投到破产要 150 秒上下，200 局 ≈ 8 小时。
   好在 `economy` 模式里已经有正确的骨架：**把实测的越线构成喂给引擎的 `crossingReturn`
   做蒙特卡洛**（`rolls = 60`，见 §4.1 的理由）。只需要改一件事：
   **`perDrop` 不能取常数，必须建成「盘面占用度的函数」**——
   否则模拟出来的局不存在上面那段正反馈，永远测不出这个开口。

## 6.13 判据自身的两个修法（这次复测顺带修掉的）

`endless` 这次报了 4 项红，查下去是**两个真因**，其余全是级联：

### 1. 「允许值集合」在脚本里被手写展开了第二份公式

`crossingReturn` 是 `Math.round(base × heat × zone × betMul)`，**取整只在最后一步做一次**。
脚本里却按「先 `round` 再 ×2」展开，于是「铜币 1 × 热度 1.5 × 热区 2」这条**同时**：
漏掉引擎实际会返回的合法值 **3**、又放进不可能出现的 **4**（实测因此报过假失败）。

修法不是「补上漏的那一档」，而是**去掉脚本里的第二份公式**：
新增 `readAllowedGains()`，**枚举调用引擎的 `crossingReturn`** 把返回值收成集合，
固定值币种（返币/大赏）也由引擎取而不再写死 3/8。引擎改取整方式或倍率表，集合自动跟着变。
顺带补了一条以前只有注释在说的判据：**固定值币种不吃任何倍率**
（按 2 币种 × 2 热区 × 3 档加注 × 4 段连落逐组重算）。

### 2. 三条「总结页」判据与「能否破产」级联

`endRun()` 的前置是「破产弹窗可见」或「已在总结页」，否则**直接 return（空操作）**。
所以「跪求后没能再破产」一红，后面「保留尊严收工」「总结页再点一次开新局」
就全部变成空操作 → 连环红，报出来的现象是「总结页坏了、盘面没复位」，
而真因在上面那条。**测的是 A，报的却是 B。**

两处解耦：

- 「跪求后能继续赌到再次破产」→ 改成**有界探针**「跪求后局被拉回：推板继续、能继续投币、账本仍平」
  （按推板节奏投满 20 枚、不等收尾）。它测的是「跪求真的把局拉回来了」；
  「局终会结束」属于经济，由 `economy` ⑤ 守（每局必须走到真实终态）。
- 「收工 / 再开新局」之前，若此刻没有破产弹窗，用**新钩子 `forceRuin()`**
  确定性地把弹窗推出来再测——这两条测的是总结页状态机，与「破产怎么来的」无关。
  上面那条红就只红它自己。

> **为什么不能图省事用 `setState('ruin')`**：它会先 `startRun()` 重开一局，
> 于是 `earned` / `begsThisRun` **全被清零**——而总结页要显示的正是这两个值
> （它读的是 `recordRun(earned, drops, begsThisRun)`）。
> 实测踩过：跪求过一次之后用 `setState('ruin')` 搭场景，总结页报「累计跪求 0」，
> **判据自己把自己搞红了**。`forceRuin()` 只走收尾那一步（清零筹码 → 进沉降 → 弹窗），
> 账本身份原样保留。
>
> 教训：**「构造一个状态」要问清哪部分是身份、哪部分只是壳。**
> 一个会把被测对象重置掉的构造器，看起来是「同一场景」，实际测的是另一件事。

### 3. 热区判据是靠「凑巧有个正在大量越线的局」才通过的

热区只占盘面宽度 `0.3 ÷ 1.36 ≈ 22%`，命中是低频事件，所以早先已经从「固定等 4 秒」
改成「等到出现热区越线为止（上限 180 秒）」。但「等」还隐含一个前提：
**盘面此刻正在产出越线**。以前这条能过，是因为前面的流程*凑巧*留下了一个正在大量越线的局
——**正是上面那个级联把它掩盖住了**（第 2 局在 160 投的长局中被中途读走，那 66 枚热区越线
全来自那个局的盘面）。级联一修，这里只剩「重开一局 + 投 1 枚」，实测 180 秒里
**一次越线都没等到**（入账集合是空的）。

修法：**判据自己把场景跑起来**——先把加注切回 ×1（手里 18 枚筹码要够投满一轮），
再按推板节奏投币，投到真的出现热区越线为止（上限 18 枚），
并顺手重新打开遥测（整页刷新会静默关掉它，见 `startRun` 的注释）。
诊断信息里带上「为此投了几枚 / 越线共几枚 / 推板在跑还是停着」，
下次再红时不用重跑就能分辨是「场景没跑起来」还是「倍率算错了」。

## 6.14 ★★ 真缺陷：推板「复位」被实现成一帧倒扫，每次开新局丢掉 16~31 枚币

这是 `endless` 那条「总结页再点一次即开新局」查出来的，**是游戏本身的缺陷，不是判据问题**。

### 现象与现场

那条判据只断言「盘面 = 预置 318 枚」，实测重开一局后是 **287 ~ 295 枚**。往下查：

```
重开时间线（每 150 毫秒采样一次）：
0ms    币 305  异常 2   drainOut
150ms  币 300  异常 18  ready
300ms  币 295  异常 23  ready     ← 之后完全稳定
异常现场（异常币飞出时的坐标与速度）：
bronze( 0.395, -0.826, -0.055) v=9.1    bronze(-0.116, -0.868, -0.072) v=9.5
bronze(-0.564, -0.918, -0.070) v=10.1   bronze(-0.747, -0.888, -0.126) v=10.0
```

三条线索一起看就定了性：

1. **丢的枚数正好等于 `anomalies` 的次数**（`318 − 287 = 31` = 异常 31 次）；
2. 全是 `bronze`、`z ≈ -0.05`（**币床最背排**）、x 横跨整条道、**速度 8 ~ 10 米/秒向下**；
3. 全部发生在重开后的**头 300 毫秒**内，`earned` 始终是 0（不是越线结算掉的）。

### 根因：`Pusher.applyTransform` 用 next 目标表达「复位」

```ts
this.body.setNextKinematicTranslation({ x: 0, y: 0, z: this.offsetZ });
```

`setNextKinematicTranslation` 表达的是「**下一步到达**这里」。`reset()` 要从行程最大处
（+0.36 米）归位到 0，引擎于是把这段位移当成**一帧内走完**，等效速度 ≈ `0.36 × 60`
≈ **21 米/秒**——推板以 21 米/秒**倒着扫过币床**。

而 `startRun` 原本的顺序是**先摆盘、后 `pusher.reset()`**：摆盘用的是「推板归位」的几何
（布局自检里那条「上层币必须在推板后缘与归位前缘之间」），可那时推板还停在上一局结束的位置。
两件事错开，背排的币正好落在推板体内，下一帧推板高速倒扫回来，把它们挤飞出机柜
（`y < -0.8`）→ 记异常 → `despawn()`。

**首局为什么不丢**：页面刚载入时推板本来就在归位点，复位是零位移，扫掠不存在。
这也解释了它为什么一直没被发现——`physics` 的「静置 10 秒不丢币、无异常」是在
**空盘上**开局的，恰好绕过它；而 `accept` 里提到 `anomalies` 的地方不看这条路径。

### 修法（两层）

1. **`Pusher.applyTransform(teleport)`**：复位走 `setTranslation` **立刻**搬过去
   （同时设同值 next，避免下一步又朝陈旧目标掠过去）。
   **复位是传送，不是运动**——这条要写在实现里，不能靠调用顺序兜底。
2. **`Game.startRun` 改成「先归位、再摆盘」**，并把 `travel` 的赋值挪到 `reset()` 之前
   （`reset()` 拿 `this.travel` 初始化 `travelForStroke`，原本是反的：第一趟行程用的是上一局的行程值）。

修完实测：时间线从 150 毫秒起就是「币 318、异常 0」并稳定；
判据加了「开局 `anomalies` 必须为 0」，并把异常币坐标一并报出来
（它们已被 `despawn`，事后查盘面看不到——`Game` 因此新增了常驻诊断 `anomalySamples`）。

### 为什么值得单独记一节

它同时是三件事的源头：

- **盘面比预置少 2 ~ 10%**，直接改变经济里「预置盘面」这份自由筹码的存量（§6.12 的输入之一）；
- **丢多少枚随推板当时的相位而变**，所以它是**逐局方差的一个来源**——P8 定标前必须消掉；
- 它一直记进 `anomalies`，但**这条路径上没有任何判据读它**（`anomalies` 在 `marks` 里被读，
  重开一局这条路径上没有）。**一个只涨不读的计数器等于没有**——诊断写下了却没人看，
  缺陷就会一直静静地躺在那里。

## 6.15 ★★ 第三个真缺陷：求解器在刚性币堆上**凭空造能量**，把币弹到 6 米高空飞出机柜

这是 P2 收口最后一次全量复测抓到的东西，也是**唯一一个由 Playwright 抓到、而
`verify-game.mjs` 九个模式全绿也没抓到**的缺陷——值得单独记清楚。

### 现象：42 条浏览器用例里恰好 1 条偶发红

```
[desktop-chrome] › tests/bot-playtest.spec.ts:142 › 满盘预置的币塔在推板作用下保持可解释的倒塌与结算
Error: expect(received).toBe(expected)   Expected: 0   Received: 1
   158 |     const state = await diagnostics(page);
 > 159 |     expect(state?.anomalies).toBe(0);
```

诡异之处有三点，每一点都排除了一个显然的解释：

1. **只有 `desktop-chrome` 红，`mobile-safari` 同一条是绿的**——同种子、同场景，说明不是逻辑错。
2. **重跑一次就绿了**（第一次复现 0/1），所以是**概率性**的，不是确定性缺陷。
3. 同一场景连跑 12 次：**4 次红**（≈ 33%），说明"偶发"其实是高频，只是单次跑常常躲过。

### 定位：把「异常」从计数变成现场

`anomalySamples`（§6.14 加的常驻诊断）直接给出答案，但第一版只有速率是不够的，
所以这次把**速度三分量 + 帧号**补进去（`Coin.velocity3()`）。抓到的三条现场：

| 帧 | x / y / z | v（vx, vy, vz） | 读数 |
| --- | --- | --- | --- |
| 136 | −1.311 / −0.538 / −0.002 | (−1.33, **−5.44**, 0.96) | 已从侧上方掉出机柜，在下落 |
| 337 | 1.323 / **4.751** / −1.383 | (0.68, −7.05, −0.36) | 折算顶点 **≈ 6.7 米**，正在下落 |
| 371 | 1.304 / 0.078 / −1.824 | (0.48, **−12.75**, −0.44) | 从 **≈ 6.3 米** 落下，12.8 米/秒 |

**关键读法**：三枚币都**几乎竖直地飞上去**（|vx| ≤ 2.1），掉回来时已经飘到侧壁之外
（`x ≈ ±1.31`，恰好压着 `|x| > 1.3` 的判据）。反推发射速度 **9 ~ 13 米/秒**。

而推板的行进速度是 `0.36 米 ÷ 0.9 秒` = **0.4 米/秒**。**放大 30 倍**——
所以这既不是"推得太猛"，也不是几何缺口，是求解器造能量。

### 一个必须正视的取舍：刚度与弹射在 `erp` 上是互相拉扯的

按纪律先做单变量对照（`setTuning` 旋钮 + 12 局重复，每局一次页面加载）：

| `erp` | 出现异常的局 | 备注 |
| --- | --- | --- |
| **0.8（出厂）** | 2/12 | 当前值，弹射可复现 |
| 0.7 | 1/12 | |
| 0.5 | 0/12 | **但 0.5 会让 95 枚币沉进地板**（见 `PHYSICS.erp` 的扫描表） |

也就是说：**把 `erp` 调低确实能压掉弹射，代价是币堆重新变软**——而币堆刚度正是
§6.10 花了一整节修出来的东西（0.8 是从 0.6~0.7 的阈值往上留的余量）。
**这两个目标在同一个旋钮上是零和的**，所以不存在"再扫一扫就好"的取值。

顺带发现：本环境的 Rapier 版本**没有** `maxCorrectiveVelocity`（修正速度上限）这个参数
（`IntegrationParameters` 只有 `dt / erp / allowedLinearError / predictionDistance /
numSolverIterations / numAdditionalFrictionIterations / numInternalPgsIterations /
minIslandSize / maxCcdSubsteps`），所以"只限制修正速度、不动刚度"这条最干净的路走不通。

### 真因判断：不是"参数没调好"，是**机台少了一面围板**

回头看几何：币床两侧只有 **0.46 米高**的护栏，护栏之上完全敞开。而 `buildCabinetShell()`
造出来的背板、顶沿、侧板——**全是纯视觉 `THREE.Mesh`，一个 Rapier 碰撞体都没有**。
真机的币床是封闭的（玻璃/亚克力罩），币在物理上不可能飞出机柜；**这里能飞出去，
是因为这台机器根本没封起来。** 弹射是"哪一天会发生"的问题，不是"会不会发生"。

### 修法（两层，配套使用）

1. **补上侧向围板**（`TableBuilder`，常量 `GLASS_TOP`）：与护栏同一个 x 平面、
   同样的厚度，从护栏顶沿（0.46）续到 1.6 米。**与护栏底沿齐平，中间不留缝**
   （留缝就会变成新的夹币点）；低摩擦（0.1）、低弹性（0.02），让币**滑回来**而不是在板里弹。
   实测与落币口（|x| ≤ 0.68）、上层台面（y ≤ 0.34）、推板体（y ≤ 0.2）全部无接触，
   只拦"飞起来的币"。
2. **速度护栏**（`COIN.maxSpeed` / `maxUpwardSpeed` + `Coin.clampSpeed`）：
   **不允许求解器凭空造能量**。两个上限都是从这台机器自身反推的，不是魔数：
   - 总速率 ≤ **8 米/秒**：机内最快的合法速度是「落币口自由落到托盘」≈ 6.3 米/秒
     （重力 −13），留 27% 余量；
   - **向上分量 ≤ 3 米/秒**：这台机器没有任何机构把币往上抛，向上的运动只有
     「落在币堆/钉子上的小反弹」（钉子弹性 0.3，按最大落速估上限 ≈ 1.9）。

   **必须逐子步施加**（`fixedUpdate` 里、`world.step()` 之前）——这一条是实测逼出来的：
   压到的**最大**速率只有 **3.6 米/秒**，远小于原来观测到的 12 米/秒。说明那 12 米/秒
   **不是某一步的巨大修正，而是连续多个子步累积出来的**；隔一帧才压一次的话，
   币早就在那几帧里被推到天上去了。

   **只在醒着的币上执行**：满盘静置时绝大多数币在睡（不参与积分、不可能有速度尖峰），
   这个判断把每子步的开销从 318 枚降到个位数。

### 结果：异常 4/12 → **0/15**，且缺陷本身没有被盖住

```
修复后，同一场景连跑 15 次（每局一次页面加载）：
  异常 0/15；速度护栏只在 2/15 局触发过，峰值 3.6 米/秒
bot-playtest.spec.ts（desktop-chrome，之前失败的那条）连跑 4 次：4/4 绿
```

**这里有一个必须写下来的判据设计问题**：围板补上之后，`anomalies` **恒为 0 就是必然的**
（币在物理上出不去了），于是它从"有效判据"退化成**恒真式**——继续拿它当验收，
通过率好看，但什么都没在测。**被围板挡住的缺陷仍然是缺陷**，只是看不见了。

所以修法配套加了两个遥测：`spikeClamps`（护栏触发次数）与 `peakSpikeSpeed`
（**压之前**的速率，即求解器实际造出来的值）。判据跟着改成问一个更准的问题：

> 不是「有没有币飞出去」（恒真），而是「**求解器还在不在造能量**」——
> `peakSpikeSpeed` 一旦冒出 12、15 这种数，即使币被挡住、`anomalies` 依旧为 0，也要红。

`probe` 模式已加两条：**纯静置 6 秒一次都不许触发护栏**（静止的币堆里不该有任何能量注入）、
**推板走完一轮后注入不得超过物理上限 6.3 米/秒**。

### 这一节的通用教训

- **`verify-game.mjs` 全绿不等于收口**：它跑的是引擎内部状态；`bot-playtest` 跑的是
  **真实浏览器 + 真实帧节奏**。这次的弹射只在真实帧率下出现（帧间 dt 抖动会加大
  推板单步位移 → 加深穿透 → 放大修正），headless 的确定性时序反而绕过了它。
  **两条链都要有**，不能只留一条。
- **"偶发红"要按频率测，不能按单次测**：单跑 1 次绿不能证明修好，也不能证明没坏。
  这次的 33% 频率是被 `--repeat-each=12` 逼出来的。**改完物理必须重复跑，取频率。**
- **同一条判据被"围板"绕过之后要主动降级**：结构性的修复会让旧判据变成恒真式，
  这时必须换一条能继续观测同一缺陷的判据（这里是"速率峰值"），否则就是
  「修好了问题，也修没了证据」。

## 7. 本环境的坑（实测记录）

1. **`tsc` / `npm run build` 必须带 `NODE_OPTIONS="--max-old-space-size=3072"`**，否则被 OOM 直接杀掉
   （退出码 137、连一行输出都没有，很容易误判成「类型全过」）。
2. **同一文件不要在同一条消息里发多个 Edit**：并行写会互相覆盖，且两个调用都报 success。
   症状是「明明改了、grep 却找不到」，随后表现为莫名其妙的 TS2339。**串行改。**
3. **bash 的 `grep` 在本环境返回空**，用专用 Grep 工具。
4. **单条命令有运行时限**：`sweep` 四档连跑（约 5 分钟）会被杀。默认两档，要更多用 `SWEEP=` 分批传。
5. **改 `src/**` 会触发 Vite 整页刷新**，正在跑的验证脚本会抛 `Execution context destroyed`。
   脚本里已对这类瞬时错误容错，但**整页刷新会重置游戏状态**，所以跑长时验证期间不要改源码。
   `clearSave` 钩子本身也会整页刷新。
6. **等新帧不要用 `waitForFrame(page, 5)`**：帧号是累计的，页面早就过了 5，调用立刻返回、读到旧快照。
   用 `waitFrames(page, n)`。
7. **断言不要建在偶然上**：判据按盘面比例而不是固定枚数；需要「某效果必然发生」时，
   场景必须让它是必然的，做不到就说明这条断言在赌运气。
8. **`npx playwright test` 会被「批量删除保护」整轮打断**：Playwright 开跑时会清空产物目录，
   产物累积到 50 个以上就被拒绝删除，报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`、测试一条都跑不了。
   已在 `playwright.config.ts` 加了出口：
   ```bash
   PW_OUTPUT_DIR="/tmp/pw-$(date +%s)" npx playwright test
   ```
   （这个保护是**按轮累计**的：本轮已经触发过，本轮内再跑也还是会被拒——换个空目录即可。）
9. **重置型测试助手会掩盖真实缺陷**：几乎所有验证模式开头都调 `clearSave()`（把钱包重置回 200），
   所以「开局买入被扣两次钱包」这种缺陷只有**不调重置**的存档迁移用例照得出来。
   每个子系统至少要留一条冷路径，并且断言绝对数（把算式写出来），不要只断言增量。
10. **计划文件 `~/.workbuddy-ai/plans/cosmic-vortex-darwin-XDipampG.md` 会被外部同步回退**：
    往里写的状态与实测记录整段丢过一次（255 行 → 198 行）。**状态写进本文件，那份只当阶段表看。**
11. **在同一个 page 里连开多局做重复实验，会在第 10 局悄悄变成空跑**：
    `startRun` 每次都从钱包扣 20（buyIn），钱包起始 200 → 第 11 局起 `buyIn` 变 0，
    **一枚币都投不出去**（`dropUntilAccepted` 全部超时），于是那一局 `循环 0`、`异常 0`，
    看起来像"平静的一局"，其实是**假绿**——它把后面的迭代全部污染成"没异常"。
    与 §6.8 是同一个根因（共享资源没复位），只是这次的受害者是实验本身。
    **重复实验要用「一次加载一局」（`--repeat-each` 让 Playwright 每局给新 page）**，
    不要在一页里连开；非要在同一页里连开，就必须每局显式复位钱包。
12. **概率性缺陷只能用 `--repeat-each` 测频率**：单跑绿说明不了任何事。这次的弹射是
    ≈33%（4/12），单跑一次有 2/3 的概率躲过去。修复后也必须用同样的频率测
    （15 局 0 异常），而不是跑一次就宣布修好。
13. **一次性定调"物理改完没坏"的完整链路**：`verify-game.mjs` 九个模式 → `tsc --noEmit`
    → `npm run build` → `npx playwright test`（两个 project）。**`verify-game` 全绿
    不代表可以收口**（见 §6.15 的教训），浏览器那一链必须一起跑。
